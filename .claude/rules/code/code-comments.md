# Code Comments

## Standard

Use JSDoc for documenting APIs. Avoid inline (`//`) and block (`/* */`) comments inside the body of
a piece of code. Prefer making the code self-explanatory through extraction and naming over
explaining it with a comment.

## When to Add JSDoc

These rules apply to all code equally; code generated by an agent is held to the same standard as
code written by a human, no more and no less.

Add JSDoc only when it documents something that is not already obvious from the declaration itself:

- Exported or complex functions, especially where the behavior, parameters, or return values are not
  obvious from the signature.
- Anything carrying business rules, edge cases, or rationale that the code alone does not convey.

JSDoc is not required when the declaration already speaks for itself:

- A simple public method, exported function, class, or constant does not need JSDoc unless it has
  additional business logic behind it, or there is information to document that is not obvious from
  how it is defined or written. When something does meet that bar, the documentation must still open
  by describing what the thing is before adding the business context (see "JSDoc Content and
  Style").
- A public class method does not need its own JSDoc when the class implements an interface on which
  that method can be documented instead. Document it once on the interface rather than repeating
  similar documentation on every concrete class, especially when multiple classes implement the
  interface.

These cases define when JSDoc is required and when an agent should add it automatically. They are a
floor, not a ceiling: a human may add JSDoc to any declaration they see fit, even one that does not
meet the bar above, and doing so is never wrong. Any JSDoc that is present, required or not, must
still follow the structure and style rules in this document, and an agent must not remove existing
documentation simply because it was not required.

## Components and Props

Do not add JSDoc to a React component, or to its props type or interface, by default. A block that
only restates what the component renders, or that says the props are "the props for `X`", carries no
information and must be omitted. Document a component or its props type only when what the component
is for is genuinely unclear, or when the component is non-standard or obscure.

The useful place for documentation is above an individual prop whose purpose or usage is not obvious
from its name and type, or a prop whose default value is applied implicitly inside the component.
Document a prop's implicit default with the `@default` tag:

```typescript
interface ProgressBarProps {
  /**
   * Whether the bar animates as its value changes.
   *
   * @default true
   */
  readonly isAnimated?: boolean;
}
```

A prop whose meaning is clear from its name and type needs no JSDoc.

## JSDoc Format

The following block satisfies every JSDoc rule in `jsdoc.mjs`:

```typescript
/**
 * Constructs the email address for a new user on signup.
 *
 * @param {string} firstName The user's first name.
 * @param {string} lastName The user's last name.
 *
 * @throws {ValidationError} If the email domain is not recognized.
 *
 * @returns {string} The constructed email address.
 */
```

The linter enforces the structure below, so match it exactly:

- The description lives in the comment body, never a `@description` tag (`jsdoc/require-description`
  with `descriptionStyle: 'body'`).
- The description begins with a capital letter and ends with `.`, `?`, `!` or a backtick. Every
  `@param`, `@throws` and `@returns` description is a full sentence ending the same way
  (`jsdoc/match-description`).
- Exactly one blank line separates the description from the first tag (`jsdoc/tag-lines`).
- Every `@param` and `@returns` includes a `{Type}` (`jsdoc/require-param-type`,
  `jsdoc/require-returns-type`). There is NO hyphen between the name or type and the description
  (`jsdoc/require-hyphen-before-param-description` set to `never`).
- Tags appear in this order, with one blank line between each group: `@param`, then `@throws`, then
  `@returns` (`jsdoc/sort-tags`). Consecutive `@param` tags are NOT separated by blank lines.
- A tag description stays to the right of the tag only when it fits on a single line. When it would
  wrap, move the entire description onto the following line(s) directly underneath the tag, indented
  two spaces, instead of letting it begin to the right and overflow (`jsdoc/check-line-alignment`
  with `wrapIndent: '  '`). This applies to every tag that takes a description, including `@param`,
  `@throws` and `@returns`.
- Many tags are disabled via `tagNamePreference` (for example `@description`, `@summary`, `@todo`,
  `@author` and access modifiers). Do not use them; check `jsdoc.mjs` before reaching for an
  uncommon tag.

A wrapped description sits underneath its tag, indented two spaces, while a short one stays inline
(here `firstName` wraps below the tag and `domain` does not):

```typescript
/**
 * Constructs the email address for a new user on signup.
 *
 * @param {string} firstName
 *   The user's first name, normalized to lowercase before the local part of the address is
 *   assembled.
 * @param {string} domain The email domain the address is created under.
 *
 * @returns {string} The constructed email address.
 */
```

JSDoc blocks (`/**`) keep the aligned leading `*` on each line. The `bare-block` styling described
below applies only to non-JSDoc block comments.

## Tag Usage

Tags like `@param` and `@returns` are not required on every documented function, method, or class.
Include them when they add information that is not obvious from the signature, such as a non-obvious
parameter, a complex shape, or a return value whose meaning the type alone does not convey. Omit
them when they would only restate what the signature already makes plain.

When parameters are documented, document them consistently: if one `@param` is included, include a
`@param` for every parameter.

This primarily constrains automatically generated documentation, to keep generated JSDoc from
mechanically restating every parameter and return type when they are simple or redundant. As with
JSDoc generally, it is a floor and not a ceiling for engineers: a human may document parameters and
returns by hand as they see fit, even when they are redundant.

## JSDoc Content and Style

- Write in formal English using complete sentences with proper grammar and punctuation. A JSDoc
  block must read as prose, never as a scattered collection of thoughts or a bare list of
  statements.
- Always open with a description of what the thing is and what it does (the API documentation)
  before adding any business context, rationale, or other detail. Visually separate that opening
  description from the business context that follows with a blank line.
- Separate logically distinct paragraphs or fragments with a blank line (a bare ` *` line) rather
  than running them together. A block that covers what the thing is, why it exists, and how it is
  used should read as a few short paragraphs, not one dense block.
- JSDoc documents an API: it must annotate a declaration (function, class, method, type, or
  constant). A JSDoc block placed on a statement inside a function body is an inline comment
  regardless of its `/** */` syntax; using JSDoc syntax does not reclassify an inline comment as API
  documentation. Do not resolve this by demoting it to a regular comment. Instead, extract the logic
  into a named constant or function that can be formally documented with JSDoc, or give it a name
  self-documenting enough that no comment is needed.
- Comments and JSDoc describe the current state of the code only, never its history. Do not write
  comparative or temporal references that go stale (for example "a flatter version of the previous
  config"); once the thing referenced no longer exists, the note is simply wrong. State what the
  code is now, not how it got there.
- Document why the code is the way it is when that is not obvious. Do not narrate the approach taken
  to write it (including the approach an agent took), and do not restate what the code plainly
  shows. Be concise: avoid redundant or over-wordy explanations.
- Reference a concrete, resolvable symbol (a function, class, method, constant, or type) with {@link
  Symbol} rather than backticks wherever the symbol can be linked. Reserve backticks for literals,
  shapes, or external names that have no symbol to link.
- When a construct has members (an interface, type, class, or enum), document each member with its
  own JSDoc block directly above that member, not with `@property` tags or a bulleted list on the
  root block. Per-member JSDoc is what editors surface through IntelliSense at each member's use
  site; documentation gathered on the root block is not.

Done well, a block with more than one concern leads with what the thing is, then separates each
subsequent concern into its own paragraph. The opening paragraph defines what the value represents;
the business context (when it applies and how it is used) follows in later paragraphs:

```typescript
/**
 * Defines the error message that is shown when attempting to submit a {@link ProgramTimeEntry}
 * where there are no entry items, {@link ProgramTimeEntryItem}, with any logged time (i.e.
 * 'minutes' > 0).
 *
 * This message represents the only error that would be expected and user-facing, as all other
 * validation errors in the {@link SubmitTimeEntrySchema} should be prevented by the form and
 * UI mechanics.
 *
 * This constant is used to key off of in the form's submit handler in order to issue logs if
 * in fact the schema validation resulted in a submit-blocking error that was not expected.
 */
export const NoLoggedTimeErrorMessage = 'At least one item must have logged time.';
```

The same constant documented badly opens with how it is used and never states what the value
actually represents, which forces the reader to infer the "what" from the "how":

```typescript
/**
 * This constant is used to key off of in the form's submit handler in order to issue logs if
 * in fact the schema validation resulted in a submit-blocking error that was not expected.
 */
export const NoLoggedTimeErrorMessage = 'At least one item must have logged time.';
```

## Inline Comments

Inline comments are a last resort, permitted only when there is genuinely no other option.

- Never describe **what** the code is doing. If a reader can understand the behavior by reading the
  code, the comment is not needed and must be removed.
- The only legitimate use is explaining **why** something non-obvious is done, and only when that
  logic cannot be extracted. If it can be lifted into a well-named function, constant, or type and
  documented with JSDoc, you must do that instead; an inline comment in its place is disallowed.
- The canonical remaining case is justifying why a type coercion is safe, because a coercion cannot
  always be abstracted into a separately documented variable or function.

## Extract Instead of Commenting

When a value or piece of logic can be named and documented, you must extract it rather than leave it
inline with a comment. Give it a name and put the explanation in JSDoc on the declaration;
inline-commenting a value that could instead be a documented declaration is disallowed. This turns a
transient "why" comment into a permanent, typed, reusable part of the API, and applies even when the
thing itself is trivial.

Extract a trivial value into a named constant when the value is simple but the reason behind it is
not. Lift the value out of the code body, where it could only be explained with an inline comment,
into a named declaration that documents itself:

```tsx
// Disallowed: the value sits inline in the markup, explained by an inline comment.
const MetricsCard = ({ children }: MetricsCardProps) => (
  // The card must fill its container's full height so the chart aligns with the legend.
  <Stack sx={{ height: '100%' }}>{children}</Stack>
);

// Required instead: the value is pulled out and the reason lives in JSDoc on the declaration.
/**
 * The height applied to the metrics card so it fills its container and keeps the chart aligned
 * with the legend rendered beside it.
 */
const ResponsiveHeightRestriction = '100%';

const MetricsCard = ({ children }: MetricsCardProps) => (
  <Stack sx={{ height: ResponsiveHeightRestriction }}>{children}</Stack>
);
```

Extract a trivial function when it exists mainly to carry the explanation of why it is needed:

```typescript
/**
 * Builds the `frame-ancestors` Content-Security-Policy directive. Canvas
 * (`https://*.instructure.com`) must be allow-listed so the application can be embedded in an
 * iframe for the LTI integration; otherwise the browser blocks the launch.
 */
const buildFrameAncestorsDirective = (): string =>
  "frame-ancestors 'self' https://*.instructure.com;";
```

## Prohibited

- TODO-style comments (`TODO`, `FIXME`, `XXX`) are forbidden.

## Line Length

- Comments and JSDoc must respect the hard limit of 100 characters and must never exceed it.
- Pack each line as close to 100 characters as possible before wrapping; do not wrap early.
