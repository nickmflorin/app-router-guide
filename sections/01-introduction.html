Chapter 1

Introduction

Don't fight the framework. This chapter is about why that sentence is the whole guide in miniature — and what it costs us when we do.

Don't fight the framework

Next.js is not a rendering engine you bolt a React app onto. It is an opinionated architecture with a specific model of how pages should be composed, where data should be fetched, and where interactivity should live. When you work with that model, an enormous amount of complexity simply disappears: loading states, request timing, cache invalidation, bundle management, and layout stability are all problems the framework has first-class answers for. When you work against it, you don't just lose those answers — you actively re-create the problems they were designed to solve, and then you hand-roll worse solutions to them.

That is the trap this guide exists to keep us out of. The patterns we've all internalized from years of traditional React — fetch in an effect, hold it in state, show a spinner, lift state up, pass callbacks down — are not neutral habits that happen to be suboptimal here. In the App Router they are load-bearing mistakes: each one forecloses a framework capability, and the foreclosures compound.

What it looks like when it compounds

Pages that take visibly long to navigate to — in production, on real networks. Spinners nested inside spinners. Content that jumps as each request lands. And the insidious part: you progressively lose the ability to adopt the tools designed to fix these problems. Streaming can't help a page whose data loads after hydration. Caching can't help a request the server never sees. Partial prerendering can't help a tree that's client-rendered from the root. The further you build into the wrong model, the more expensive the road back — the refactoring becomes a never-ending battle.

Read the docs

Seriously — read them. Not as API reference when something breaks, but as a description of a model. The App Router docs are unusually good at explaining why each convention exists: why layouts don't re-render, why loading.tsx is a file and not a prop, why caching is opt-in, why the client boundary is a directive. Most of the patterns in this guide are not clever inventions; they are the documented, intended usage. The single biggest upgrade available to us as a team is to stop treating this stack like the React we already know and to step outside the traditional model we've all become accustomed to.

This guide is the map, not the territory. Every chapter links to the primary sources — official Next.js and React documentation — collected in §17 References.

The stakes

The architecture and approach you use now sets the stage for the rest of the product's life. That's not a platitude; it's the compounding math of a codebase. Every new page copies the patterns of the page before it. Every hook written around a client-side fetch becomes a dependency of the next feature. Conventions harden in months; unwinding them takes years.

I say this as someone who has tried to refactor ojl-tracker out of exactly these problems, repeatedly. It is a never-ending battle, and the debt was cheapest on the day it was created. We do not want a re-recraft — imagine how much more confusing the Slack channels, the product names, and the team names would become.

The good news

You're smart, and you'll figure this out. None of this is beyond anyone on this team — it's a mental-model swap, not a skill gap. But it has to be deliberate: if we keep building into this thing without understanding how the technology wants to be used, we will end up in a world of pain that gets harder to escape every sprint. The whole point of this document is to make the deliberate path the easy one.

How this guide is organized

§2 defines what we're optimizing — the goals behind every pattern, each tagged as universal React or Next-specific. §3 is the pivot of the document: where React and Vercel are heading, what actually happens when an App Router page renders, and why the traditional mental model fails quietly now and loudly later. Parts A–C then elaborate each goal family with its patterns, Part D applies all of it — a worked example, the "Signs You're Doing It Wrong" checklist, and before/after case studies from our own codebase.

Two chip systems annotate every practice throughout:

  • React / Next.js — whether the practice applies to any React app or is specific to (or dramatically amplified by) the App Router.
  • Critical / Very important / Important — how much it matters that we follow the practice. Critical items are foundational: getting them wrong undermines the architecture itself. Very important items are our default on every page, with occasional exceptions. Important items are strong habits with the lowest ceremony to deviate from. Wherever a practice has legitimate exceptions, they're named — so you know what a valid exception looks like, and the rule never feels arbitrary.
