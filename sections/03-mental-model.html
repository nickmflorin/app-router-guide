Chapter 3

The Mental Model

This is the pivot chapter. If you take one thing from this guide, take this: the model you learned from years of traditional React is not the model this stack is built on — and the ecosystem is moving away from it, not toward it.

3.1 The direction of travel

For roughly a decade — call it 2013 to 2022 — "a React app" meant one thing: the server sends an empty HTML shell and a JavaScript bundle; the bundle boots; components mount; effects fire; data is fetched; the page assembles itself in the browser. Everything we internalized as "how React works" — fetch-in-effect, loading flags in state, lifting state up, client routers, spinners — is machinery for surviving inside that model.

That model is not where React is going. It hasn't been for years, and the trajectory is unambiguous:

  • React Server Components moved rendering — and with it, data access — to the server, making "component that runs in the browser" the explicitly-marked exception rather than the assumption.
  • Actions moved mutations to the server, making "POST to an API route, then juggle client state" unnecessary for the common case.
  • Suspense and streaming moved loading states out of components and into the tree structure, making "this component shows its own spinner" an anti-pattern rather than a convention.
  • Next.js 16's caching model (opt-in caching, partial prerendering by default when enabled) is built on the assumption that most of a page is server-rendered and cacheable, with dynamic regions marked by Suspense — an assumption an SPA-style app violates on every page.
  • The React Compiler removes the memoization busywork that made "just put everything in one big client component" feel pragmatic.

Notice the pattern: every major primitive React and Vercel have shipped since 2020 assumes a server-first architecture. None of them help — several actively can't function — in a tree that is client-rendered from the root. The feature-level details live in §16; what matters here is the direction. Writing SPA-style code in the App Router isn't "sticking with classic React." It is building on the legacy model of a framework that has already left, betting the product's future against the platform's roadmap.

The one-sentence version

Traditional React asks: "how do I get data into my components?" Server-first React asks: "which parts of my UI can't be finished on the server, and why?" — and treats every such part as a cost to be justified.

3.2 What actually happens when a page renders

In the App Router, every component is a server component by default. When a request comes in, the server executes your component tree — running your async components, awaiting your data — and streams the result to the browser as HTML, immediately, including real content for everything that was knowable and reserved fallbacks for everything that wasn't. Client components — only the subtrees you explicitly mark with "use client" — are the only parts that ship JavaScript, hydrate, and become interactive.

Three consequences of this model are worth internalizing, because they invert traditional-React instincts:

  • Data access is a render-time concern, not a lifecycle concern. A server component doesn't "mount and then fetch" — it simply awaits what it needs while rendering. There is no timing to coordinate, no "is the data here yet?" state to manage. An entire category of client-side complexity — effects, request state machines, race conditions, stale closures — exists only on the other side of the client boundary. This is the deeper reason backend code has always felt simpler than frontend code: the server deals in one request → one response, while the client juggles user interactions, network variability, browsers, extensions, ad blockers, and time itself. SSR moves work from the hard side to the easy side.
  • The bundle is the exception, not the app. Server components ship zero JavaScript. Your app's JS payload is exactly the sum of its "use client" subtrees — which is why boundary placement (§4) is an architectural decision, not a style preference.
  • Navigation re-renders on the server too. Client-side navigations fetch the new route's server output (the RSC payload), not JSON-for-you-to-assemble. Layouts persist without re-rendering; only the changing segments re-render. The router — not your state management — owns the page's identity.

The app directory is your app — not "routes"

It's tempting to see app/ as the router's configuration area: thin page.tsx files that immediately hand off to the "real" components living in components/. That inversion is exactly backwards. The app directory is the application — its structure, its layouts, its containers, its core content. Everything related to the core parts of a page belongs there; the pieces that slot into that scaffold are what live outside it.

This is also the answer to a question worth asking yourself: why does Next.js use file-based routing at all? Because the filesystem makes the page's composition statically knowable. Layouts nest by directory. Loading and error boundaries are files, so the framework knows where they are before any code runs. Code splitting falls out per-segment for free. Prefetching a link means the router already knows exactly what the destination needs. Every one of those capabilities depends on the tree being declared in the filesystem rather than assembled at runtime in the browser. A five-line page.tsx that delegates everything to a giant client component doesn't just "move code around" — it hides the entire page from the framework.

3.3 Why the old mental model bites you later

The dangerous thing about SPA-style code in the App Router is that it works at first. The page renders. The data arrives. Nothing warns you. The costs arrive later, on real networks, at real scale, and by then they're structural:

And the failure modes compound, because each one blocks the escape route from the others:

Habit you keepTool you lose
Fetch after hydration (effects, client query hooks)Streaming and loading.tsx — there's nothing to stream; the server finishes instantly with an empty shell.
"use client" at the page/layout levelServer components below it — the entire subtree is client forever; every child you add ships to the bundle.
Requests the server never seesThe whole caching model — "use cache", revalidation, request dedupe. You rebuild caching by hand, per hook.
Mutations via hand-rolled API routesActions, revalidatePath/revalidateTag — read-your-writes consistency becomes your problem, solved with things like consistency tokens.
Client state for tabs, filters, visibilityShareable URLs, server-resolvable first render, and the router's back/forward behavior — all gone at once.

Read the left column against our own codebase and the pattern is uncomfortable — §15 does exactly that, file by file. The point of this chapter isn't blame; every one of those habits was the correct professional instinct in 2019. The point is that they are instincts, and instincts don't update from warnings — they update from understanding the machine underneath. That's what Parts A through C are for.
