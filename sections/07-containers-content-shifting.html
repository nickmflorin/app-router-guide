Chapter 7 · Part B — Contain the Unknown

Containers & Content Shifting

Containers are the known half of "contain the unknown": they render immediately, they reserve accurate space, and everything uncertain happens inside them. Get this right and nothing on the page ever moves; get it wrong and every request landing is a small earthquake.

7.1 What content shifting costs

Content shift is the page rearranging itself while the user is already using it. The costs are concrete: the paragraph they were reading jumps out from under their eyes; the button they were about to press moves and they press what replaced it; scroll position stops meaning anything while the page is still "settling." Each shift also re-runs layout for everything below it — on long pages, repeatedly. And users read instability as unreliability: a page that jolts three times before it settles feels broken even when every request succeeded.

This is measured in the field as Cumulative Layout Shift (CLS), one of Google's Core Web Vitals — every unexpected shift is scored by how much of the viewport it moved, and the scores accumulate. But the metric is just the symptom sheet. The disease has one cause: something rendered without its space having been reserved. And SPA-style pages have it worst, because when all data arrives after hydration (§3), every region is a late arrival landing in unreserved space, one request at a time, in whatever order the network decides.

7.2 The container doctrine

The fix is a strict separation of ownership. Split every uncertain region into two roles:

  • The container is known. It renders immediately, from the server, with the page's first paint — its chrome (card, border, heading, toolbar) and, critically, its dimensions. It is part of the scaffold, so it belongs with the structure (§3's app directory, §7.4 below). React Critical
  • The occupants are swapped inside it. First the fallback, then the content — both rendered into the container, both sized to fit the reservation. The Suspense boundary sits just inside the container's walls (§8).

Three rules make the separation real, and each one exists because breaking it produces a specific visible bug:

7.3 Reserving space honestly

A reservation is a promise about the future — the container claims the space its content will need. The strategies, in order of preference:

  • Exact dimensions, when the content's size is knowable. A paginated table with 10 rows of 44px is 440px before any data exists — rows-per-page times row height is the reservation. Media is the canonical case: always give images explicit width/height (or aspect-ratio) so the browser reserves before loading — next/image enforces this. React Critical
  • min-height, when only the floor is knowable. Reserve the minimum honest footprint — enough that the common case doesn't shift, growth is rare and downward. A dishonest reservation (a token 40px under a region that always renders 400px) is just a smaller earthquake.
  • Flex-grow and scroll, for the main content region. The strongest reservation is the viewport itself: the page frame is a column — header and toolbars sized by content, the content region flex: 1 with overflow-y: auto. The page as a whole never changes height; tables can grow, filters can change the row count, and all of it happens inside a scroll area whose outer box is fixed. This is the default posture for every list/table page we build. React Very important
app/(admin)/reports/layout.tsx — the flex-grow-and-scroll frameexport default function ReportsLayout({ children }) {
  return (

      <ReportsHeader />

          Whatever streams, loads, or grows in here, the frame holds. */}
      <main className="min-h-0 flex-1 overflow-y-auto">

}

Two more shift sources worth closing while we're here: fonts — a late-swapping webfont reflows every line of text; next/font preloads and applies size-adjusted fallbacks so text renders in its final metrics from the start Next.js Very important — and conditionally-injected UI (banners, alerts, toolbars that appear after a check): give them reserved slots or overlay them; never insert them into the flow above existing content.

7.4 Containers live in the scaffold

Where should containers be rendered? As high as their stability allows — which usually means in the layout or page, as part of the app directory's scaffold (§3). Next.js Very important The payoff is navigation: layouts persist across route changes — they don't re-render when you move between sibling pages (§3.2). A container rendered in the layout is therefore stable not just against its own content loading, but against navigation itself: moving from one program's report to another swaps what's inside the containers while the frame — header, tabs, table chrome — never repaints. The page stops feeling like a sequence of pages and starts feeling like an application.

This is also the bridge to §9: once containers live in the layout, each one can be filled independently — its own data, its own Suspense boundary, its own error state. That's exactly what parallel routes formalize (§9.3): slots in the layout's scaffold, filled as independent units.
