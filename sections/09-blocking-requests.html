Blocking Requests

Every await is a gate, and everything rendered behind it waits. The goal: make the region behind any single blocking request as small as possible, and make independent requests run at the same time — on the server and on the client alike.

9.1 What sits behind a request

When a component awaits, everything it renders waits with it. That's the blocking scope of the request — and it's determined entirely by where in the tree the await happens. An await at the top of the page puts the whole page behind one gate: header, navigation, static text, all of it held hostage by the slowest fetch. The same await, pushed down into the component that actually uses the data, holds only that region — the rest of the page renders and streams immediately (§8.2).

So the rule is positional: await where the data is used, not where it's convenient to write. React Critical This is the same force behind §10's independence argument — self-fetching children don't just decouple the code, they shrink each request's blast radius to the component that needed it.

9.2 Parallel by default

The second half of the discipline: independent requests must not wait for each other. Sequential awaits in one component are the classic server-side waterfall — each fetch starts only after the previous one finishes, and the region's wait is the sum of its requests instead of the max: React Critical

Two mechanics worth knowing precisely. Sibling async server components render concurrently — composing self-fetching components (§10) gives you parallelism for free, which is another reason independence beats drilling. React Critical And a call into the deduped data layer starts the request whether or not you await it — so when a fetch is genuinely slow and needed below, you can kick it off early (const p = getRows(id) with no await) and let the component that needs it await the same deduped promise later. Start early, await late, and only where needed.

Genuinely dependent requests — B needs A's answer — are the one honest waterfall. The discipline there: confine the chain to the smallest region that needs its result. React Very important

9.3 Parallel routes: independence with a file address

§7.4 put the containers in the layout; §10 made the regions self-fetching; §8 gave each one a boundary. Parallel routes are the framework formalizing that whole pattern as filesystem structure: a layout declares named slots (@header, @summary, @table), each slot is its own mini-page, and the framework fills them independently — each with its own loading.tsx, its own error.tsx, its own streaming lifecycle. Next.js Very important

app/programs/[id]/layout.tsx — slots arrive as propsexport default function ProgramLayout({ children, header, summary }) {
  return (
    <div className="flex h-full flex-col">
      {header}
      <div className="grid grid-cols-[1fr_320px] gap-6 min-h-0 flex-1">
        <main className="overflow-y-auto">{children}</main>
        <aside>{summary}</aside>
      </div>
    </div>
  );
}

When to reach for a slot instead of a plain component: when the region deserves route-level independence — its own loading.tsx/error.tsx files, participation in navigation, or different content per sub-route. Nick's canonical example: a page header. If the header is static, it's just layout markup — no slot needed. If the header depends on server data (program name, status badge, owner), a @header slot gives it an error and loading lifecycle that can't take the table down with it, and vice versa. One convention matters in practice: default.tsx is what a slot renders when the current URL doesn't match anything inside it (typically: re-render nothing-specific, or return null) — omit it and navigation into unmatched states 404s the whole route. Define it for every slot. Next.js Critical

9.4 The client has waterfalls too

Everything above has a client-side mirror, and it's the expensive one — each client-side gate is a full network round trip plus a render cycle. The patterns to hunt: dependent query chains (useQuery/useSWR hooks gated on each other's results — profile → organization id → dashboard data, each hop serialized after hydration), and fetch-after-mount cascades, where a component fetches, renders children, and the children then begin their fetches. Our audit found 53 enabled:-gated dependent queries in one app — 53 serialized round trips that a server component tree would have resolved in one pass. React Critical

The fixes, in order: move the chain to the server, where the dependency is an in-datacenter hop inside one request (§9.2's dependent-chain pattern) — this is the structural fix and it's usually available; collapse the chain's key, so the client asks one question ("dashboard for current user") and the server resolves the intermediate steps; and where client fetching is legitimate (§11.3), make sibling queries independent — two hooks with no enabled: coupling fire in parallel.
