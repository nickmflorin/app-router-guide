Chapter 11 · Part C — Decouple the Parts

Dedupe & Caching

§10 argued that components should ask for their own data instead of being wired together — and that the repetition is free. This chapter is the receipts: the layers that collapse many identical questions into one real request, on the server and on the client.

11.1 The layers

Think of every data access as a question — getProgram(42) — asked by whichever components need it, however many times they like. Between the question and the origin (your API, your database) sit deduplication and caching layers. Each layer has a different lifetime, and the lifetimes are the whole game:

11.2 The server data layer

The pattern that makes all of Part C work: every server data access lives in one module, and every function in it is wrapped in cache(). Next.js Critical Components never call fetch or the database directly — they call the data layer, from anywhere in the tree, as many times as composition requires.

data/programs.tsimport { cache } from "react";
// This import turns any leak into a client bundle into a build error.
import "server-only";

/* This is a per-request memo: any component may call it with the same id,
   and it executes once per request — no matter who asks or how often. */
export const getProgram = cache(async (id: string) => {
  const res = await fetch(`${API_URL}/programs/${id}`, { headers: await authHeaders() });
  if (!res.ok) throw new ProgramError(res);
  return res.json() as Promise<Program>;
});

Two subtleties worth knowing. First, fetch itself dedupes identical calls within a render pass Critical — but cache() is the habit to build, because it also covers database clients, SDKs, and computed values, and it gives the function a single authoritative home. Second, cache()'s lifetime is one request: it is a dedupe mechanism, not a performance cache. User A's request never sees user B's data through it, which is exactly what you want for anything personalized.

When data is not personalized and survives across requests — templates, org lists, filter options, reference data — promote it one layer up with "use cache": Next.js Very important

data/templates.tsimport { cacheLife, cacheTag } from "next/cache";

export async function getFormTemplates() {
  // The output is cached across requests AND users.
  "use cache";
  // The acceptable staleness is declared, not implied.
  cacheLife("hours");
  // The tag is a handle for targeted invalidation.
  cacheTag("form-templates");
  return api.templates.list();
}
actions/templates.ts"use server";
import { revalidateTag } from "next/cache";

export async function createTemplate(input: TemplateInput) {
  await api.templates.create(input);
  // Every reader updates — no callbacks up the tree, no refetchAll().
  revalidateTag("form-templates");
}

Note what the mutation does not do: it doesn't call a callback up to some parent, doesn't set a consistency token in the URL, doesn't orchestrate a refetchAll(). It invalidates the tag, and every component that reads getFormTemplates() — wherever it sits in the tree — gets fresh data on the next render. That's §10.4's "communicate through the cache" made concrete.

11.3 The client data layer

Some data genuinely must load from the client — it only exists after an interaction, or it polls, or it's driven by rapidly-changing client state. For that: one shared hook per question, built on SWR (or React Query), keyed canonically. Never raw fetch in a component, never fetch-in-effect. React Critical

✕ Hand-rolled — no dedupe layer exists
every component, separatelyconst [program, setProgram] = useState(null);
const [isLoading, setIsLoading] = useState(true);
useEffect(() => {
  fetch(`/api/proxy/programs/${id}`)
    .then(r => r.json())
    .then(setProgram)
    .finally(() => setIsLoading(false));
}, [id]);
/* Two components means two requests, two
   loading states, two error paths, and
   zero sharing. */
✓ Shared hook — the key IS the dedupe
hooks/useProgram.tsimport useSWR from "swr";

export function useProgram(id: string) {
  return useSWR<Program>(`programs/${id}`, fetcher);
}
/* Any number of components call this with
   the same id: one cache entry, one request,
   revalidated on focus, updated by mutate(). */
Client cache is a complement, not the architecture

SWR's cache lives in browser memory: it evaporates on a hard navigation and starts empty for every visitor. It cannot make first render fast — only the server layers can (that's Part A). The division of labor: server cache for what the page is born with; client cache for what it learns afterwards. If you find most of a page's data flowing through SWR, the problem isn't the caching — the fetching is on the wrong side of the boundary.
