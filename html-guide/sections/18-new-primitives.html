Chapter 18 · Appendix

New Primitives

The reference catalog behind §1's direction of travel: the primitives React 19 and Next.js 16 ship, what each one is for, and a working example of each. Skim the map, then read the entries you need.

Before the catalog, a nudge: a lot of this is genuinely new, and a fair amount of it is easy to miss. The platform ships APIs faster than most of us read the changelogs, and many of them exist precisely to delete work we're still doing by hand: a hook that replaces a whole isLoading/errors state pair (useActionState), a value that replaces a debounce (useDeferredValue), a component that replaces a mount/unmount dance (Activity), a compiler that replaces a wall of useMemo (the React Compiler). Half the reason this appendix exists is discovery: to put the current server-first toolkit in one place, so the next time you're about to reach for a manual workaround, you can check here first and find that the framework already ships the thing. If an entry below is new to you, that is exactly the point; skim the map for the names you don't recognize.

Two things to notice as you read. First, almost every primitive here assumes the server-first architecture the rest of this guide describes: actions assume mutations live on the server, use() assumes promises are created on the server and read under Suspense, the caching primitives assume the server renders something worth caching. They are the payoff of the model, not add-ons to it. Second, these are primitives, not goals: the chapters own the patterns, and this appendix owns the API surface. Where a primitive already has a home in a chapter, the entry links there instead of repeating the doctrine.

18.2 Actions and mutations

Server Functions ("use server")

A server function is an async function that runs on the server but is callable from client code as if it were local. React serializes the call across the network; Next.js wires it to an endpoint automatically. This is the primitive that makes our 73 pass-through proxy handlers (§17) unnecessary for mutations: no route handler, no manual fetch, and end-to-end type safety, because the function's signature is the contract. 

actions/programs.ts"use server";
import { revalidateTag } from "next/cache";

export async function archiveProgram(id: string) {
  await api.programs.archive(id);
  // Every reader of this tag refreshes; no callbacks up the tree.
  revalidateTag(`program-${id}`);
}

The calling side, with its pending state, is the self-contained button pattern that §5.7 owns; the post-mutation refresh channel is §13.2's invalidation story; the architecture, and why to prefer actions over proxy routes, is the focus of §5.10. Docs: React: "use server" · Next.js: Updating Data.

<Form> (next/form)

Next's <Form> extends the HTML form with prefetching, client-side navigation, and progressive enhancement. Its behavior depends on the action prop: a string makes submission a GET navigation with the fields serialized into search params (the URL-writing search input of §8.2, with the destination's loading.tsx prefetched); a function makes it an action-backed mutation form. 

components/programs/ProgramSearch.tsximport Form from "next/form";

export function ProgramSearch() {
  /* A string action means: navigate to /programs?q=… on submit,
     client-side, with the target's shared UI prefetched. */
  return (
    <Form action="/programs">
      <input name="q" placeholder="Search programs" />
      <SearchButton />
    </Form>
  );
}

Note the page rendering this is still a server component: no directive, no hooks. Docs: Next.js: Form · React: <form>.

useActionState

Binds a form to an action and gives you back the action's last result as state, plus the dispatch function and a pending flag. This is where validation errors live in the actions world: the action returns them, React renders them, and nobody hand-rolls an errors/isSubmitting state pair. (If you're searching the docs: this hook replaced the earlier useFormState from react-dom.) 

components/programs/CreateProgramForm.tsx"use client";
import { useActionState } from "react";
import { createProgram } from "@/actions/programs";

export function CreateProgramForm() {
  /* state is whatever the action last returned: validation errors here.
     The third value is the pending flag for the whole submission. */
  const [state, formAction, isPending] = useActionState(createProgram, { errors: null });
  return (
    <form action={formAction}>
      <input name="name" />
      {state.errors && <FieldErrors errors={state.errors} />}
      <Button type="submit" isLoading={isPending}>Create</Button>
    </form>
  );
}

Docs: React: useActionState.

useFormStatus

Reads the pending state of the nearest ancestor form from anywhere inside it. Its point is composition: a shared submit button can disable itself in any form it's dropped into, without a single prop being threaded to it (the §12 spirit, applied to forms). 

components/forms/SearchButton.tsx"use client";
import { useFormStatus } from "react-dom";

export function SearchButton() {
  // True while the enclosing form's action is in flight.
  const { pending } = useFormStatus();
  return (
    <Button type="submit" isLoading={pending}>
      Search
    </Button>
  );
}

Docs: React: useFormStatus.

useOptimistic

Shows the expected result of an action immediately, while the real mutation runs. If the action fails, React reverts to the true value automatically; when revalidated data arrives, it confirms. Use it for cheap, likely-to-succeed writes where waiting even 300ms feels broken. Note how it fits the loading doctrine of §10: the existing content is never replaced by a spinner; it just updates. 

components/programs/LikeButton.tsx"use client";
import { useOptimistic } from "react";
import { likeProgram } from "@/actions/programs";

export function LikeButton({ id, count }: { id: string; count: number }) {
  const [optimisticCount, setOptimisticCount] = useOptimistic(count);
  return (
    <form
      action={async () => {
        /* Paint count + 1 now; revert automatically if the action throws,
           confirm when the revalidated count arrives. */
        setOptimisticCount(optimisticCount + 1);
        await likeProgram(id);
      }}
    >
      <Button type="submit">{optimisticCount} likes</Button>
    </form>
  );
}

Docs: React: useOptimistic.

18.3 Async UI and transitions

use()

Reads a promise (or a context) during render, suspending until it resolves. Its headline pattern: a server component starts a fetch without awaiting it, hands the promise across the boundary as a prop, and a client component reads it with use() under the Suspense boundary the server already rendered (§10). The request begins on the server, the HTML streams, and the client never runs a fetch-in-effect. 

app/programs/[programId]/page.tsxexport default async function ProgramPage({ params }: PageProps) {
  const { programId } = await params;
  // Deliberately not awaited: the promise itself crosses the boundary.
  const notesPromise = getProgramNotes(programId);
  return (
    <Suspense fallback={<NotesSkeleton />}>
      <ProgramNotes notesPromise={notesPromise} />
    </Suspense>
  );
}
components/programs/ProgramNotes.tsx"use client";
import { use } from "react";

export function ProgramNotes({ notesPromise }: { notesPromise: Promise<Note[]> }) {
  // Suspends here; the server-rendered boundary above shows the fallback.
  const notes = use(notesPromise);
  return <NotesList notes={notes} />;
}

Docs: React: use · Next.js: Fetching Data.

useTransition

Marks an update as non-blocking and gives you its pending flag. In this stack it is the engine of the self-contained mutation button (§5.7) and of no-fallback refinements (§10): the old UI stays interactive while the new state, or the server action, resolves. When to reach for it, and the three canonical uses, are covered in §10.7. 

components/programs/ArchiveButton.tsx"use client";
import { useTransition } from "react";
import { archiveProgram } from "@/actions/programs";

export function ArchiveButton({ id }: { id: string }) {
  const [isPending, startTransition] = useTransition();
  return (
    <Button
      isLoading={isPending}
      onClick={() => startTransition(() => archiveProgram(id))}
    >
      Archive
    </Button>
  );
}

Docs: React: useTransition.

useDeferredValue

Returns a copy of a value that lags behind on purpose, so urgent updates (the keystroke) outrun expensive ones (re-filtering a thousand-row table). This is the fix for the table problem in §10: the input stays crisp, the table catches up when it can, and nothing flashes a spinner. 

components/programs/ProgramFilter.tsx"use client";
import { useDeferredValue, useState } from "react";

export function ProgramFilter({ programs }: { programs: Program[] }) {
  const [query, setQuery] = useState("");
  // The input re-renders with query; the heavy table follows with this.
  const deferredQuery = useDeferredValue(query);
  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <ProgramTable programs={programs} filter={deferredQuery} />
    </>
  );
}

Docs: React: useDeferredValue.

<Activity>

Hides a subtree without unmounting it: state, scroll position, and DOM survive, and hidden trees render at low priority. Before reaching for it, apply the §8.3 ladder: tabs that represent where the user is belong in the URL. Activity is for the panels that genuinely remain client state (interaction, not identity) and are expensive to remount. 

components/editor/EditorPanels.tsx"use client";
import { Activity } from "react";

export function EditorPanels({ active }: { active: "editor" | "preview" }) {
  return (
    <>
      {/* The hidden panel keeps its unsaved edits instead of remounting. */}
      <Activity mode={active === "editor" ? "visible" : "hidden"}>
        <DraftEditor />
      </Activity>
      <Activity mode={active === "preview" ? "visible" : "hidden"}>
        <DraftPreview />
      </Activity>
    </>
  );
}

Docs: React: Activity.

<ViewTransition>

Animates enter/exit/update/shared-element transitions using the browser's native View Transition API, coordinated with Transitions and Suspense, declared in JSX instead of hand-rolled animation state.

Experimental: do not adopt yet

As of this writing, <ViewTransition> is available only in React's canary and experimental channels, not in stable React 19.2. It's in this catalog because it shows where the platform is going (animation as a tree concern, like loading states in §10), not because we should ship it. Watch the React: ViewTransition page for stabilization.

18.4 Utilities

useEffectEvent

Extracts the non-reactive part of an effect: the returned function always sees the latest props and state, but is not a dependency, so the effect stops re-running (and re-connecting, re-subscribing, re-firing) when those values change. Stable as of React 19.2. It is a scalpel for the few legitimate effects that remain after §17's Finding 3 is fixed; it is not a license to write more effects. 

components/jobs/JobStatusToast.tsx"use client";
import { useEffect, useEffectEvent } from "react";

export function JobStatusToast({ jobId, theme }: { jobId: string; theme: Theme }) {
  // Always sees the current theme, without being an effect dependency.
  const onDone = useEffectEvent(() => toast.success("Job finished", { theme }));
  useEffect(() => {
    // Re-subscribes only when the job changes, not when the theme does.
    const sub = jobs.subscribe(jobId, () => onDone());
    return () => sub.unsubscribe();
  }, [jobId]);
  return null;
}

Docs: React: useEffectEvent.

useId

Generates ids that are stable across server render and hydration. Hand-written or randomly generated element ids are a hydration-mismatch factory in an SSR world; this is the sanctioned replacement, chiefly for accessibility wiring. 

components/forms/EmailField.tsx"use client";
import { useId } from "react";

export function EmailField() {
  // Identical on the server and in the browser, unique per instance.
  const id = useId();
  return (
    <>
      <label htmlFor={id}>Email</label>
      <input id={id} type="email" />
    </>
  );
}

Docs: React: useId.

useSyncExternalStore

The correct way to subscribe to anything that lives outside React: browser APIs, third-party stores, singletons. It takes a subscribe function, a snapshot reader, and a server snapshot so SSR and hydration render consistently, which is exactly the failure mode of doing this with useEffect + useState. 

hooks/useOnlineStatus.ts"use client";
import { useSyncExternalStore } from "react";

function subscribe(onStoreChange: () => void) {
  window.addEventListener("online", onStoreChange);
  window.addEventListener("offline", onStoreChange);
  return () => {
    window.removeEventListener("online", onStoreChange);
    window.removeEventListener("offline", onStoreChange);
  };
}

export function useOnlineStatus() {
  /* Subscribe, read the client snapshot, and provide a server snapshot
     so the SSR pass and hydration agree. */
  return useSyncExternalStore(subscribe, () => navigator.onLine, () => true);
}

Docs: React: useSyncExternalStore.

cache()

Per-request memoization for server functions: same arguments, one execution, per request. It is the foundation of the server data layer, and it already has a full treatment in §13.2; it appears here only so the catalog is complete. Docs: React: cache.

useLinkStatus

Reads the pending state of the enclosing <Link> from a descendant component: an inline hint for navigations that can't be instant (prefetching disabled, or a dynamic route without a loading.tsx). Prefer route-level fallbacks and prefetching first (§4.5); reach for this when a specific slow transition needs feedback at the link. 

components/nav/LinkPendingDot.tsx"use client";
import { useLinkStatus } from "next/link";

export function LinkPendingDot() {
  // Must render inside a Link; true until the navigation commits.
  const { pending } = useLinkStatus();
  /* Fixed-size and always rendered, so toggling it never shifts layout
     (the §9 container rule, at the scale of a dot). */
  return <span aria-hidden className={pending ? "dot dot-pending" : "dot"} />;
}

Docs: Next.js: useLinkStatus.

<Profiler>

Wraps a subtree and reports what rendering it actually cost, per commit, to an onRender callback. Use it to turn "this page feels slow" into a named component and a number before optimizing anything; pair it with the React DevTools performance tracks. Docs: React: Profiler.

18.5 The React Compiler

The compiler (1.0, October 2025) memoizes automatically at build time: it analyzes component code and skips re-renders that provably change nothing, which is the work useMemo, useCallback, and React.memo asked humans to do by hand. Two consequences for us. First, new code should not hand-roll memoization; write plain idiomatic components and let the compiler prove what's stable. Second, the compiler rewards the exact discipline this guide teaches: small, decoupled components with narrow props (§12, §14) give it clean units to optimize, while God components (§5.9) give it one giant opaque one. It changes none of the architecture in this guide; it removes the busywork that made bad architecture feel cheap. Docs: React: React Compiler · Next.js: reactCompiler.
