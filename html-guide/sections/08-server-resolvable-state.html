Chapter 8 · Part A: Maximize the Known

Server-Resolvable State

The first render is a function of the request. Nothing more. State the request carries (the URL, route params, search params, cookies) is known; state living in a component's memory is invisible to the server, and every pixel that depends on it is unknown. This chapter is about putting state where the server can see it, which mostly means: use the URL more.

8.1 The principle: state the server can see is content the server can finish

When a request arrives, the server knows exactly four kinds of state: the path (which page, and its route params), the search params (the query string), the cookies, and the headers. That's the complete list. Everything the first render shows must be derived from those, so every piece of UI state you store anywhere else is a piece of UI the server cannot finish. Next.js Critical

Watch what happens when a filtered table keeps its filter in useState. The server renders the page with… which rows? It doesn't know the filter: the state won't exist until a client component mounts and initializes it. So the table can't be server-rendered with real content; it becomes a client component that fetches after hydration, and we've bought the entire Part B problem set (spinners, shifting, waterfalls; §4.2) for a filter that would have fit in twelve characters of query string. Move the same state into the URL and the request is the state: the server reads ?status=active, renders the right rows into HTML, and the "state management" is the platform's.

The bonus features come free, and they're not small. State in the URL is shareable (paste the link, get the view), refresh-proof (F5 reproduces the page instead of resetting it), navigable (back/forward walk through filter history), deep-linkable (dashboards, emails, and docs can point at a specific view), and supportable ("send me the link" replaces "describe every dropdown you touched"). A view that lives in component state has none of these; it dies with the tab.

8.2 The URL is the state manager

What belongs in it: filters, search text, sort column and direction, pagination, tabs, view modes (table/grid), date ranges, expanded-group state on reports, selected item when it drives a panel; in short, anything that describes which view of the data the user is looking at. Next.js Very important The reading side is a server page prop; both are Promises in Next 16: 

app/programs/[programId]/reports/page.tsxexport default async function ReportsPage({ params, searchParams }: PageProps) {
  const { programId } = await params;
  const { q = "", page = "1" } = await searchParams;

  /* The URL fully determines this render. The same link produces the same
     page for anyone, the rows arrive as HTML, and there is no client-side
     state to hydrate, restore, or lose. */
  const reports = await getReports(programId, { q, page: Number(page) });

  return <ReportTable reports={reports} />;
}

The writing side you've already seen: an interactive leaf updates the query string with router.replace() inside a transition, and the server page re-renders with fresh rows: §5.8 has the search input, §10.5 builds the full table around it, and §5.6 covers the Suspense boundary the reading leaf must carry. Two writing details worth pinning down:

  • replace vs push is a product decision about the back button. Keystrokes and minor refinements should replace (back shouldn't step through every character typed); discrete view changes (a tab, a page number) can push so back walks the user's actual path.
  • Reading a search param makes that part of the render request-time, which is exactly why it must sit behind a Suspense boundary under PPR (§5.6): the static shell prerenders, and the param-dependent region is a deliberate dynamic hole (§4.4).

8.3 Tabs are routes in disguise

The clearest instance of the whole principle, and the smell we most need to unlearn, is tabs held in useState. A tab bar is a set of views with identities. "Which view am I looking at?" is precisely the kind of state the URL exists to answer, and holding it in memory forfeits everything at once: the link can't say which tab it points at, refresh snaps back to the default, the server can't render the active panel's content, and, since every panel must be reachable by a client-side click, all the panels ship to the client, rendered or not (§6).

✕ Tabs in state: the smell
ProgramView.tsx"use client";

export function ProgramView() {
  const [tab, setTab] = useState("reports");

  return (
    <>
      <TabButton
        active={tab === "reports"}
        onClick={() => setTab("reports")}
      >
        Reports
      </TabButton>
      {tab === "reports" && <Reports />}
      {tab === "roster" && <Roster />}
    </>
  );
}
View identity held in memory: not shareable, not refresh-proof, invisible to the server, and every panel ships to the client whether shown or not.

The header and tab bar render once in layout.tsx and persist across tab changes (§3.1). Each tab is a segment whose page.tsx is server-rendered, streamed, and prefetched by its Link, and each brings its own loading.tsx and error.tsx boundaries (§10.2).

With segments, each tab is a page: server-rendered with real content, prefetched by its <Link> before the click (§4.5), and addressable from anywhere. The layout (header, tab bar, containers) persists across switches without re-rendering (§3.1, §9.4). The tab bar itself is a row of links; its only client concern is knowing which one is active: 

components/program/ProgramTabs.tsx"use client";

import { usePathname } from "next/navigation";

/* A tab bar is a row of links. Active state comes from the URL, so it
   survives refresh, travels in a shared link, and the server renders the
   right panel on the first response. usePathname doesn't need a Suspense
   boundary; only the query string is per-request (§5.6). */
export function ProgramTabs({ programId }: { programId: string }) {
  const pathname = usePathname();

  return (
    <TabList>
      {TABS.map((tab) => (
        <TabLink
          key={tab.href}
          href={`/programs/${programId}/${tab.href}`}
          active={pathname.endsWith(tab.href)}
        >
          {tab.label}
        </TabLink>
      ))}
    </TabList>
  );
}

When segments are too heavy for the case (small toggle-like tabs inside one page), the fallback is still the URL: a ?view= search param the server page switches on, not useState. The ladder is segments, then a search param, then (for genuinely cosmetic switches) state, and each step down the ladder should be a deliberate decision, not a habit. Next.js Very important

8.4 Writing the URL: transitions, stale content, and optimistic tabs

Reading the URL is half the contract; the other half is writing it, because writing the URL is how a client leaf forces the server to re-render. Next.js Critical When a leaf calls router.replace() with a new query string, the router performs a client-side transition to the same route: the server re-renders the page with the new searchParams, and the fresh RSC payload merges into the tree in place (§4.5). Watch the network tab while it happens: no document reload, just a small RSC request carrying the re-rendered segments. The URL write is the refetch.

Three refinements turn that mechanic into UI that feels instant. First, wrap the write in a transition: the App Router treats navigations as transitions, so an already-revealed Suspense boundary keeps its current content instead of re-showing a fallback (§10.5), and your own useTransition gives you isPending as the loading indicator. Second, show the stale content while the new render is in flight: dim it against isPending, or reach for useDeferredValue when the results are client-rendered; both worked examples live in §10.5. Third, and this is the one that makes tabs feel native: update the selection optimistically.

The problem with URL-derived tab state alone: the active highlight comes from searchParams, which only changes when the server render lands. Click a tab and the highlight lags behind by the length of the render. React 19's useOptimistic closes that gap: set the optimistic value immediately inside the transition, and React reconciles it with the URL-derived value automatically when the new payload arrives (or reverts it if the navigation fails): 

ViewTabs.tsx (inner; the baked-in Suspense wrapper of §5.6 is omitted)"use client";

export function ViewTabsInner() {
  const searchParams = useSearchParams();
  const router = useRouter();
  const [isPending, startTransition] = useTransition();

  /* The URL is the source of truth; the optimistic value fronts for it
     while the server render is in flight. */
  const urlView = searchParams.get("view") ?? "reports";
  const [view, setOptimisticView] = useOptimistic(urlView);

  return (
    <TabList data-pending={isPending}>
      {TABS.map((tab) => (
        <TabButton
          key={tab.value}
          active={view === tab.value}
          onClick={() =>
            startTransition(() => {
              setOptimisticView(tab.value);
              const params = new URLSearchParams(searchParams);
              params.set("view", tab.value);
              router.replace(`?${params.toString()}`);
            })
          }
        >
          {tab.label}
        </TabButton>
      ))}
    </TabList>
  );
}
The clicked tab highlights instantly: setOptimisticView applies before the server render starts, the transition carries the URL write, and when the fresh payload lands the optimistic value reconciles with the URL-derived one automatically. If the navigation fails, React reverts the highlight for free. The interaction is never blocked by the page render; only the panel content waits, dimmed, per §10.5.

The result is the best of both worlds from §8.3's ladder: the URL stays the source of truth (shareable, refresh-proof, server-rendered), and the interaction feels as immediate as any useState tab bar. The same recipe applies to any URL-backed control: filters, sort toggles, pagination, view switches.

8.5 Cookies: preferences that follow the user, not the URL

Some state should survive across pages and sessions but has no business in a link: the collapsed sidebar, a table-density preference, the dismissed-announcement flag, theme. Put those in cookies (the other channel the request carries), and the server resolves them at first render, which is what kills the flash-of-wrong-state that localStorage approaches are doomed to (the server can't read localStorage, so it always renders the default first and corrects after hydration). Next.js Very important 

app/(dashboard)/layout.tsximport { cookies } from "next/headers";

export default async function DashboardLayout({ children }: LayoutProps) {
  /* A preference that must survive across pages and sessions, and that the
     server needs at first render to avoid a flash of the wrong layout:
     a cookie, not useState, not localStorage. */
  const store = await cookies();
  const collapsed = store.get("sidebar-collapsed")?.value === "true";

  return <Shell sidebarCollapsed={collapsed}>{children}</Shell>;
}

The same caveat as search params applies: reading cookies makes that part of the tree request-time, so under PPR it belongs inside a deliberate dynamic region (§4.4). The rule of thumb for choosing the channel: the URL describes the view, cookies describe the viewer. A filter is the view: anyone with the link should get it. A collapsed sidebar is the viewer: it would be bizarre in a shared link.

8.6 What genuinely stays client state

The point is not that useState is bad; it's that it should hold interaction, not identity. Ephemeral, mid-gesture, this-tab-only state is exactly what it's for: the text in an input before it's committed to the URL (the debounced draft in §10.5), the open/closed flag of a dialog or menu living in its leaf (§5.7), hover and focus, an in-flight optimistic value, a drag mid-drag. React Very important

Two questions sort every case. Would the user expect it back after a refresh, or want it in a shared link? Then it's the URL (view) or a cookie (preference). Does the server need it to render real content? Then it must be server-resolvable, full stop. Content the server can't finish is Part B's territory, and we only go there deliberately. If both answers are no, it's interaction state: keep it in the leaf, in memory, where it costs nothing.
