Chapter 7 · Part A: Maximize the Known

Bundle Size & Code Splitting

§6 was about the mechanics of keeping JavaScript out of the first render. This chapter is about the judgment: which dependencies are worth their weight, why a single heavyweight component can undo the entire known/unknown split, and what all that shipped JavaScript actually costs the people using the app.

7.1 The JavaScript you ship is a tax on the known

Part A is about maximizing what the server can deliver as finished HTML. Every kilobyte of client JavaScript works against that goal from the other side: the browser has to download it, parse it, and execute it before the page is truly interactive, and until then the "known" content you worked so hard to render on the server is sitting there looking ready while doing nothing. A page can be server-rendered and still feel broken if it ships a megabyte of JavaScript in front of the first interaction. So bundle size is not a separate performance chore bolted on at the end; it is the same goal as the rest of Part A, measured at the network instead of the render.

The good news is that the App Router splits code by route automatically: a given page ships the JavaScript for its own tree, not the whole app. The bad news is that this automatic splitting is easy to defeat, and the rest of this chapter is a tour of the three most common ways we do it: pulling in a component so heavy it drags the page down, fusing the known and the unknown into one undeferrable lump, and importing through barrel files that quietly negate tree-shaking.

7.2 The wholesale-component trap

Here is the most instructive failure, because it shows how bundle size and the known/unknown thesis are the same problem. Picture a reports page with a data table. Look at what is actually knowable at first render: the toolbar, the title, the column headers, the footer, the pagination controls, the empty-state and the row skeleton are all known immediately. The only genuinely unknown part is the body rows, because those depend on data we have to fetch.

Now reach for a wholesale data grid, an all-in-one client component like MUI's DataGrid that owns the toolbar, the headers, the rows, the sorting, the virtualization, and the footer in a single package. You have just fused everything back together. The frame that was knowable is now trapped inside a client component that cannot render until its bundle downloads and its data arrives.

The trap is specifically that a wholesale grid takes all three of your best tools off the table at once. You cannot wrap Suspense around just the body rows, because the rows aren't a separate component. You cannot show a skeleton over just the rows while the header stays put, for the same reason. And you cannot defer the import of just the rows and render the known frame immediately, because the frame and the rows are one import. The composed version, a server-rendered table shell with a Suspense boundary around a server component that awaits the rows, gets all three for free. 

app/reports/hours/page.tsx (server component)import { Suspense } from "react";

export default function HoursPage() {
  return (
    <table>
      {/* The frame is known on the first byte: server HTML, no client JS. */}
      <TableToolbar />
      <TableHead columns={COLUMNS} />
      {/* Only the rows are unknown, so only the rows suspend. */}
      <Suspense fallback={<RowSkeleton rows={10} />}>
        <HoursRows />
      </Suspense>
      <TableFooter />
    </table>
  );
}

The same contrast, seen as an actual page rather than a stack of boxes, makes the trade-off obvious. It is the anatomy view from §2, aimed at one region: watch what happens to the table when the frame is fused to the rows versus kept separate from them.

7.3 Heavyweight imports, and fallbacks that stay light

Sometimes you genuinely need a heavy client component: a rich text editor, a charting library, a map, a spreadsheet grid whose interactivity you can't rebuild by hand. The rule there is not "never use it," it is keep it out of the first-render bundle and give it a light fallback. In our own ojl-tracker work, the data-heavy tables are loaded lazily for exactly this reason: the route paints its frame immediately, and the heavy grid streams in behind a skeleton rather than blocking the whole page on its download.

The mechanics of the dynamic import (the ssr: false option, the top-level declaration rule) live in §6.3; what matters here is the fallback. The fallback must be lighter than the thing it stands in for. A common mistake is to hand the loading state another heavy component, or a spinner that itself pulls in an animation library. The fallback should be cheap, static markup that reserves the right space (§9): a plain skeleton, sized to match. 

components/reports/HoursGrid.tsx"use client";
import dynamic from "next/dynamic";

/* The heavy grid is pulled out of the first-render bundle and loaded on
   demand. Its fallback is deliberately minimal: a static skeleton that
   reserves the right height, not another heavy component. */
const DataGrid = dynamic(() => import("./HeavyDataGrid"), {
  loading: () => <RowSkeleton rows={10} />,
  ssr: false,
});

export function HoursGrid({ rows }: { rows: Row[] }) {
  return <DataGrid rows={rows} />;
}
Deferring a heavy import is a fallback, not a fix

Lazy-loading a wholesale grid is strictly better than shipping it in the first bundle, but it is still the second-best answer. It hides the weight; it doesn't remove it, and the user still pays the download the moment the component is needed. Whenever the frame is genuinely knowable, prefer the composed server-rendered table from §7.2 and reserve the heavy client component for the parts that truly need its interactivity.

7.4 Barrel files quietly defeat code splitting

A barrel file is an index.ts that re-exports everything in a folder so callers can write import { Button } from "@/ui" instead of reaching into the specific module. It reads nicely and it is a reliable way to inflate every bundle that touches it. The problem is that importing one name from a barrel makes your route depend on the whole barrel: the bundler now has to consider every module the barrel re-exports, and anything with a side effect, or anything tree-shaking can't prove is unused, comes along for the ride.

✕ Barrel: one name pulls the whole package
components/Toolbar.tsx"use client";import { Button } from "@/ui";
Pulling from the @/ui barrel adds the whole library to this route's graph: Button drags in Modal, DatePicker, RichTextEditor, and everything else the barrel re-exports.
✓ Direct: one name pulls one module
components/Toolbar.tsx"use client";import { Button } from "@/ui/button";
Imports only Button's module; nothing else in @/ui joins this route's bundle.

Modern bundlers and Next's optimizePackageImports can claw some of this back, and for well-behaved side-effect-free packages the damage is smaller than it used to be. But the reliable habit is to not create the problem: import from the specific module, and don't ship index.ts barrels for your own component libraries. This is also where bundle size meets component design: barrels tend to grow around files that hold too many components, which is the same instinct §14 argues against. One component per file, imported directly, is both cleaner to read and cheaper to ship.

7.5 What bloated pages actually cost

It is worth being concrete about who pays, because "big bundle" sounds abstract and the costs are not. They land on the two groups we care most about: the people using the app and the people building it.

Who pays What it costs them
Users, on first load A longer wait before the page is interactive, even after the server HTML is on screen. The gap between "looks ready" and "responds to a click" is pure JavaScript download, parse, and execution time.
Users, on every navigation Heavier route bundles make client transitions feel sluggish, and the pain scales with the worst device and network in your user base, not your laptop on office wifi. Mobile and poor connections feel it first and worst.
Users, on data Megabytes of JavaScript are megabytes of someone's mobile data plan and battery, spent re-shipping code that a server render would have turned into a few kilobytes of HTML.
The team, on build Bigger dependency graphs mean slower builds and slower type-checks, a tax on every commit and every CI run, and a compounding drag on how fast the team can move.
