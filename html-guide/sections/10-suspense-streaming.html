Suspense & Streaming

Loading is not a component concern. It's a structural one. Suspense moves "what shows while we wait" out of components and into the tree, where the framework can stream around it. This chapter covers how suspension works, what triggers it, and the loading-state doctrine that follows from it.

10.1 How Suspense actually works

A <Suspense> boundary is a declaration about the tree: "everything below this point may not be ready yet; here is what to show in its place." When a component inside the boundary suspends (it's waiting on something asynchronous), React walks up the tree to the nearest boundary, renders its fallback there, and, when the wait resolves, swaps the real content into the exact same slot. The component itself never knows any of this happened. That's the entire point: the waiting is handled above the component, by structure, not inside it, by state.

What triggers a Suspense boundary

These are framework mechanics, worth knowing precisely: Critical

  • An async server component awaiting inside the boundary: the canonical App Router case. The server streams the fallback, keeps working, and streams the content when the await resolves.

Suspense is not a server-only feature

Notice that three of those five triggers fire in the browser. It is a common blind spot to think of Suspense as a server-rendering mechanism: a client component that reads a promise with use(), a Suspense-enabled data hook, or a lazy() chunk all suspend and reveal through the same boundary. The boundary doesn't care which side of the network its child runs on; it cares only that the child is waiting. So the whole doctrine of this chapter, that the boundary owns the loading state and the component never rolls its own, applies to genuinely-client subtrees exactly as it does to server data.

Just as important is what does not trigger suspension: a fetch inside useEffect is invisible to React. Nothing suspends, no boundary activates, no streaming happens; the framework doesn't even know the component is waiting. Every hand-rolled isLoading flag in our codebases exists because the fetching pattern opted out of the mechanism that would have made it unnecessary.

Boundaries don't re-trigger on updates

A boundary that has already revealed content will not revert to its fallback when an update inside it suspends during a transition: router navigations and startTransition updates keep the existing content visible while the new content prepares. React 19.2 further batches how server-streamed boundaries reveal. The fallback is a first-render device; everything after first render should follow the stale-content rules in §10.4.

10.2 Streaming: Suspense on the server

Without Suspense, server rendering is all-or-nothing: the response can't start until every fetch on the page finishes, so the slowest request sets the time-to-first-byte for the entire page. With Suspense boundaries, the server streams the page in order of readiness: the shell (layout, containers, everything known) goes out immediately, and each suspended region follows as its data resolves, injected into its reserved slot without re-rendering anything around it. (Making the waits themselves small and parallel, rather than just streaming around them, is §12's subject.)

Two placement rules follow: Next.js Critical

  • loading.tsx is a route-level Suspense boundary the framework wires up for you: it wraps the page and shows instantly on navigation. Use it for the route transition, but treat it as the coarsest tool: a whole-page skeleton is exactly the page-level skeleton we avoid (§10.4). Prefer a loading.tsx that renders the page's known scaffold, with granular boundaries inside the page doing the real work.
  • Granular boundaries around each data-dependent region: one per self-fetching component (§13.3), placed inside the known container (§9). This is also what Partial Prerendering builds on: with cacheComponents, everything outside your Suspense boundaries becomes the static shell served instantly, and the boundaries define exactly where dynamic content streams in.

It helps to see what these files literally are. You never write the wrappers; Next.js assembles them around your page from the files' presence alone:

Every boundary is a decision: an unblocked paint, for a fallback

A Suspense boundary is not free structure; it is a trade, and it helps to name both sides of it. What you buy: the page stops waiting for that region's data. The server ships the shell the moment it is ready, the browser paints it, and the slow region streams into its slot later; without the boundary, that one fetch holds the entire response hostage (the first diagram above). What you pay: something must now occupy that region's space in the meantime. A boundary forces a fallback into existence, and the fallback is real UI: it has to reserve honest dimensions (§9), look intentional next to finished content, and hand off to the real thing in a seamless swap.

That makes "should this suspend?" a per-region judgment call, not a rule you can apply mechanically. Most of the time the answer is yes: suspend and stream, because one slow fetch must not set the time-to-first-paint for content that was ready. But the trade tilts the other way when a good fallback cannot be authored. If the region's height is genuinely unknowable in advance, the swap will shift content no matter how careful the skeleton is; if the data resolves in a handful of milliseconds, the fallback is a flash of noise that was never worth painting. In those cases it is legitimate to let the server block on the fetch, provided the wait is kept small and parallel (§12).

The two questions to ask per region

First: is this data slow enough, often enough, that the rest of the page should not wait for it? If no, block and render it finished. If yes: can I draw a fallback that reserves this region's true shape? If yes, suspend. If no, fix the container until the answer is yes (§9); shipping the shift is not one of the options.

10.3 Components must not define their own loading states

React Critical A component that owns its own loading indicator, whether that's a spinner, a skeleton, or any other placeholder, has made three decisions it has no business making: that it is worth waiting for (its parent's composition decides that), where the waiting UI appears (the boundary above decides that), and what the rest of the page does meanwhile (it can't know). The costs show up immediately:

  • Loading becomes un-composable. Compose three self-spinning components and you get three spinners resolving at different moments: spinner cascades, each swap shifting layout. With boundaries, the composing parent decides: one boundary around all three, or one each, without touching any of them.
  • The loading UI is welded to the data mechanism. Move the fetch from client to server, add a cache, wrap it in a transition, and the hand-rolled isLoading plumbing has to be rewritten every time. A fallback on a boundary survives all of those changes.
  • It's invisible to the framework. Streaming, PPR, and transition semantics all operate on boundaries. A component-owned spinner opts out of every one of them.

10.4 Skeletons: scoped, colocated, structural

The container doctrine is §9's subject: containers known and immediate, fallback and content swapped inside them, one shared footprint, and neither occupant bringing its own chrome. All of it applies verbatim to fallbacks: the fallback is simply the container's first occupant. React Critical What belongs to this chapter is the fallback itself, the skeleton:

  • Scope skeletons per server component (or per client component when needed), never per page. Very important A page-level skeleton is a second, shadow implementation of the entire page layout. It drifts the moment anyone changes the real page, and nobody remembers to update it; the maintainability cost compounds with every route. A per-component skeleton is small, sits next to the component it mirrors (StatsRow.tsx / StatsSkeleton.tsx), and changes in the same PR when the component changes.
  • Keep skeletons structural, not photorealistic. They exist to hold reserved space and signal "coming": a few bars matching the content's rough geometry. The more detailed the skeleton, the faster it drifts.
  • Skeletons appear exactly once per region: on first load. Never on refetch; that's the next section.

10.5 Refetches show stale content, never fallbacks

React Critical A skeleton answers the question "what goes here?", a question that's only ever open once. On a refetch, the answer is already on screen. Replacing real content with a skeleton destroys information the user was looking at, resets their scroll and reading position, and shifts layout twice for zero benefit. The rule, in stale-while-revalidate terms: existing content is never replaced while new content loads; loading is only ever indicated, alongside the stale content.

The tools, by situation:

  • URL-driven server UI (the default case): transitions. The App Router performs navigations inside startTransition, so when a filter changes the URL, the already-revealed table stays on screen while the server re-renders with the new searchParams; the Suspense boundary does not revert to its fallback. Wrap the router.replace() in your own useTransition and isPending is your indicator. Assembled end to end in the first example below.
  • Client-fetched data: SWR / React Query already behave this way: data keeps its previous value while isValidating/isFetching is true (use keepPreviousData when the key changes). Bind your indicator to isValidating; never gate the content on it.
  • Client-rendered results of a fast-changing value: useDeferredValue. When the value drives client-side rendering or client-fetched queries (an autocomplete, search-as-you-type against the client cache), render against the deferred value; value !== deferredValue drives the dimmed opacity. Same presentation rule, client-side mechanism. Shown in the second example below.

Example: URL-driven server UI, kept stale through a transition

The first bullet, the default case, assembled end to end. Notice it's the whole guide in one example: the URL is the state (§8), the input and the dim-wrapper are client leaves (§5), the rows are a server component fetching by searchParams, and the fallback appears exactly once: 

app/reports/page.tsx - server: the URL is the inputexport default async function Page({ searchParams }) {

          requires every request-time read to sit inside a Suspense boundary. */}

        <SearchInput />

export function SearchInput() {

  const router = useRouter();

✓ StaleContent: client shell, dims what passes through
StaleContent.tsx"use client";
export function StaleContent({ children }) {
  const { isPending } = useQueryTransition();

  /* The children are the server-rendered rows,
     passing through the boundary (§5.4). This
     shell only indicates loading; it never
     replaces them. */
  return (
    <div style={{ opacity: isPending ? 0.6 : 1 }}>
      {children}
    </div>
  );
}

The flow on a filter change: the input calls router.replace() inside the shared transition → the server re-renders ReportRows with the new query → because it's a transition and the boundary has already revealed, the stale rows never leave the screen; they just dim until the fresh server render streams in and swaps. The skeleton appeared exactly once, at first load. And note what ReportRows gets for free by being a server component: it only ever runs when the data is finished, so the unknown-vs-empty question (§10.6) collapses: undefined can't reach it, and the empty check is honestly just "finished and empty." One caveat to keep it honest: don't put a key tied to the query on the Suspense boundary: a remounted boundary is "new content" and will re-show its fallback.

Example: client-rendered results of a fast-changing value

The third bullet. Here nothing touches the server or the URL: the data is already on the client, and the fast-changing value is each keystroke. useDeferredValue gives the same stale-content behavior with a purely client mechanism: the input re-renders instantly with the fresh value, while the expensive results below are allowed to lag one render behind and dim until they catch up: 

ProgramFilter.tsx - client: search-as-you-type over client data"use client";

export function ProgramFilter({ programs }) {
  const [query, setQuery] = useState("");

  /* deferredQuery lags behind query while React re-renders the heavy list.
     The input stays instantly responsive; the results are allowed to be one
     keystroke stale. */
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;

  const matches = useMemo(
    () => programs.filter((p) => p.name.toLowerCase().includes(deferredQuery.toLowerCase())),
    [programs, deferredQuery]
  );

  return (
    <>
      <Input value={query} onValueChange={setQuery} />

      {/* Same presentation rule as the server case: stale results stay
          visible and dim; they are never swapped for a spinner. */}
      <div style={{ opacity: isStale ? 0.6 : 1 }}>
        <ProgramList programs={matches} />
      </div>
    </>
  );
}

Two mechanisms, one rule. The transition example indicates with isPending; this one indicates with query !== deferredQuery. In both, the existing results never leave the screen, and nothing below the input ever collapses into a spinner. (The middle bullet, client-fetched data, needs no example of its own: SWR and React Query give you this behavior out of the box; just bind your indicator to isValidating and never gate content on it.)

10.6 Loading, data, and empty are three separate questions

The deepest of the loading-state mistakes is structural: the if (isLoading) … else if (!data) … else … chain. It welds three independent questions into one sequence, and every branch is wrong in some state:

  • "Is a request in flight?" A status, true on first load and on every refetch. It decorates the UI (indicator, dimming); it must never decide which UI renders; that's how refetches turn into skeletons.
  • "Do we have data?" A question about knowledge: undefined means we don't know yet (no request has finished). It's answered by the presence of a value, not by the loading flag.
  • "Is the data empty?" Only askable after we have knowledge: the request finished and returned nothing. Empty state visibility has exactly one condition: finished, and empty. It has nothing to do with loading.

This is also why the data layer must never default missing data to an empty array. React Critical data ?? [] feels like defensive convenience, but it erases the distinction between "unknown" and "known-empty"; downstream code can no longer tell whether to show a skeleton or an empty state, and the classic bug appears: an "No results" flash on every first load, before the data arrives. undefined is information. Preserve it end to end, and let the leaf that renders decide.

The full state space, made explicit. Every cell reachable, every cell deliberate:

Knowledge (data) Status (request) Render
undefined (unknown) in flight (first load) Fallback/skeleton, inside the reserved container. The only skeleton case.
undefined (unknown) failed Error state via the boundary (error.tsx / error boundary), never an empty state.
Row[], n > 0 revalidating Stale rows + indicator. Content never unmounts.
[] (known-empty) finished Empty state. The only condition that shows it: finished and empty.
[] (known-empty) revalidating Empty state + indicator: an empty result being refreshed is still known-empty.
Row[], n > 0 idle Rows. The happy path.

One container, one skeleton, ever

The table reads row by row; watched as one container over its lifetime, it collapses to a single rule: the skeleton appears exactly once, on first load, while the answer is unknown. The moment the first response lands, the container has something honest to show forever after: rows if there are rows, a real empty state if there are none. Every fetch from then on (revalidation, filter change, a mutation's refresh) decorates that content instead of replacing it: same UI, dimmed or badged while the request is in flight. And the treatment does not depend on what the content is. A known-empty list being refreshed keeps its empty state and gains the indicator, exactly like a populated list keeps its rows; the skeleton does not get to come back just because the container happens to be empty.

10.7 Transitions

Every state update in React is urgent by default: React drops what it is doing and re-renders to reflect it as fast as it can. React Very important useTransition (and its standalone form startTransition) marks an update as non-urgent: React prepares the resulting UI in the background while the current one stays visible and interactive, and if a genuinely urgent update (a keystroke) lands mid-render, React abandons the background work, handles the keystroke, and restarts. One flag, and three behaviors fall out of it, each a distinct tool.

Transitions keep the old UI alive

The callout in §10.1 noted that a boundary already showing content will not fall back to its skeleton when an update inside it suspends during a transition. That behavior is how you get updates that don't flash, and it is the same doctrine as §10.5, one level up: don't blank what you already have just because something newer is on the way. This is the reason writes to router-owned state, a navigation or a searchParams update (§8.2), belong in a transition: the current page stays live while the next view prepares, and the isPending flag from useTransition shows progress alongside the old content instead of replacing it. 

SortSelect.tsx - client leaf: a router write that keeps the table alive"use client";

export function SortSelect({ current }: { current: string }) {
  const router = useRouter();
  const [isPending, startTransition] = useTransition();

  return (
    <Select
      value={current}
      disabled={isPending}
      onChange={(sort) =>
        startTransition(() => {
          /* A router write: the server re-renders the page.
             Inside a transition, the table's boundary keeps
             its revealed rows instead of falling back. */
          router.push(`/programs?sort=${sort}`);
        })
      }
    />
  );
}
While the server prepares the new rows, isPending is true: dim the table, disable the select, badge the header; the old UI never blanks. The end-to-end version of this pattern is the §10.5 example.

Transitions defer expensive work

The second use has nothing to do with data: a state update whose re-render is expensive. Re-filtering a large list, re-laying-out a chart, switching a heavy tab: wrap the update in startTransition and the typing, clicking, and scrolling stay responsive while the heavy render runs at low priority, restarted rather than blocking whenever the user does something urgent. Two caveats from the React docs are worth knowing. A transition cannot drive a controlled text input: the input's own value is urgent by definition (the user must see their keystroke), so the transition carries the expensive derived state and the input updates normally. And when the value whose update you would defer is not yours to wrap (it arrives through props or a store), useDeferredValue is the same mechanism applied to a value instead of an update: the type-to-filter example in §10.5. 

ProgramSearch.tsx - client: urgent keystroke, non-urgent filter"use client";

export function ProgramSearch({ all }: { all: Program[] }) {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState(all);
  const [isPending, startTransition] = useTransition();

  function onInput(next: string) {
    // Urgent: the keystroke must paint immediately.
    setQuery(next);
    startTransition(() => {
      // Non-urgent: rendered in the background, restarted
      // if another keystroke lands mid-render.
      setResults(filterPrograms(all, next));
    });
  }

  return (
    <>
      <Input value={query} onChange={onInput} />
      <ResultsList items={results} dimmed={isPending} />
    </>
  );
}
Two updates from one keystroke. The input's own value is the urgent one and paints at once; the expensive re-filter of results runs at low priority and never blocks typing.

Async transitions: actions and pending state

React 19 extended transitions to async functions, which the docs call actions: startTransition(async () => { … }). isPending flips to true at the first call and stays true until every update the action scheduled has landed, which is exactly the lifecycle a submit button needs; this is the machinery behind firing a server action from a leaf (§5.7), where isPending drives the button and the result object carries the failure (§5.8). Errors thrown inside an action surface to the nearest error boundary, and optimistic UI (useOptimistic, §8.2) reverts automatically when the action fails. One sharp edge from the docs: after an await, further state updates inside the action must be wrapped in startTransition again, or they lose their transition marking. 

ArchiveButton.tsx - client leaf: an async action"use client";

export function ArchiveButton({ programId }: { programId: number }) {
  const [isPending, startTransition] = useTransition();

  return (
    <Button
      disabled={isPending}
      onClick={() =>
        startTransition(async () => {
          /* The action: awaited inside the transition, so
             isPending covers the server round trip AND the
             re-render its revalidation triggers. */
          const { error } = await archiveProgram(programId);
          if (error) toast.error(error);
        })
      }
    >
      {isPending ? "Archiving…" : "Archive"}
    </Button>
  );
}
The same machinery as the publish button in §5.7: isPending flips at the first line and holds until every update the action scheduled has landed, so the button cannot double-fire and the label is honest.

The API reference for useTransition and useDeferredValue is in §19.3; the caveat list lives in the React docs.
