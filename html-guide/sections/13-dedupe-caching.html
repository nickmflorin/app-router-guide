Chapter 13 · Part C: Decouple the Parts

Dedupe & Caching

§12 argued that components should ask for their own data instead of being wired together, and that the repetition is free. This chapter is the receipts: the layers that collapse many identical questions into one real request, on the server and on the client.

13.1 The layers

Think of every data access as a question (getProgram(42)) asked by whichever components need it, however many times they like. Between the question and the origin (your API, your database) sit deduplication and caching layers. Each layer has a different lifetime, and the lifetimes are the whole game:

Layer Lifetime What it does Importance
fetch() dedupe One render pass Identical fetch(url, options) calls during a single server render share one request. Automatic. Critical
React.cache() One request Memoizes any server function per request: DB queries, SDK calls, computations. Same args → one execution. Critical
"use cache" Cross-request Caches a function/component's output across requests and users; cacheLife sets duration, cacheTag enables targeted invalidation. Opt-in (Next 16, cacheComponents). Very important
SWR / React Query Client session Key-based client cache: components sharing a key share one entry and one request; stale-while-revalidate keeps it fresh. Critical

13.2 The server data layer

The pattern that makes all of Part C work: every server data access lives in one module, and every function in it is wrapped in cache(). Next.js Critical Components never call fetch or the database directly: they call the data layer, from anywhere in the tree, as many times as composition requires. 

data/programs.tsimport { cache } from "react";
// This import turns any leak into a client bundle into a build error.
import "server-only";

/* This is a per-request memo: any component may call it with the same id,
   and it executes once per request, no matter who asks or how often. */
export const getProgram = cache(async (id: string) => {
  const res = await fetch(`${API_URL}/programs/${id}`, { headers: await authHeaders() });
  if (!res.ok) throw new ProgramError(res);
  return res.json() as Promise<Program>;
});

Two subtleties worth knowing. First, fetch itself dedupes identical calls within a render pass Critical, but cache() is the habit to build, because it also covers database clients, SDKs, and computed values, and it gives the function a single authoritative home. Second, cache()'s lifetime is one request: it is a dedupe mechanism, not a performance cache. User A's request never sees user B's data through it, which is exactly what you want for anything personalized.

When data is not personalized and survives across requests (templates, org lists, filter options, reference data), promote it one layer up with "use cache": Next.js Very important 

data/templates.tsimport { cacheLife, cacheTag } from "next/cache";

export async function getFormTemplates() {
  // The output is cached across requests AND users.
  "use cache";
  // The acceptable staleness is declared, not implied.
  cacheLife("hours");
  // The tag is a handle for targeted invalidation.
  cacheTag("form-templates");
  return api.templates.list();
}
actions/templates.ts"use server";
import { revalidateTag } from "next/cache";

export async function createTemplate(input: TemplateInput) {
  await api.templates.create(input);
  // Every reader updates: no callbacks up the tree, no refetchAll().
  revalidateTag("form-templates");
}

Note what the mutation does not do: it doesn't call a callback up to some parent, doesn't set a consistency token in the URL, doesn't orchestrate a refetchAll(). It invalidates the tag, and every component that reads getFormTemplates(), wherever it sits in the tree, gets fresh data on the next render. That's §12.4's "communicate through the cache" made concrete.

13.3 The client data layer

Some data genuinely must load from the client: it only exists after an interaction, or it polls, or it's driven by rapidly-changing client state. For that: one shared hook per question, built on SWR (or React Query), keyed canonically. Never raw fetch in a component, never fetch-in-effect. React Critical

✕ Hand-rolled: no dedupe layer exists
every component, separately"use client";

const [program, setProgram] = useState(null);
const [isLoading, setIsLoading] = useState(true);
useEffect(() => {
  fetch(`/api/proxy/programs/${id}`)
    .then(r => r.json())
    .then(setProgram)
    .finally(() => setIsLoading(false));
}, [id]);
Two components asking this way means two requests, two loading states, and two error paths, with zero sharing between them.
✓ Shared hook: the key IS the dedupe
hooks/useProgram.ts"use client";

import useSWR from "swr";

export function useProgram(id: string) {
  return useSWR<Program>(`programs/${id}`, fetcher);
}
Any number of components can call this hook with the same id: one cache entry, one request, revalidated on focus and updated by mutate().
Client cache is a complement, not the architecture

SWR's cache lives in browser memory: it evaporates on a hard navigation and starts empty for every visitor. It cannot make first render fast; only the server layers can (that's Part A). The division of labor: server cache for what the page is born with; client cache for what it learns afterwards. If you find most of a page's data flowing through SWR, the problem isn't the caching: the fetching is on the wrong side of the boundary.

13.4 Choosing the layer

The data is… Use Example
Needed at first render, personalized cache() in the server data layer program detail, user profile, permissions
Needed at first render, shared across users "use cache" + cacheLife/cacheTag templates, org lists, filter options, reference data
Born from an interaction SWR / React Query shared hook search-as-you-type results, autocomplete
Live / polling SWR with refreshInterval job status, notifications badge
Changed by a mutation Action + revalidateTag (server) / mutate() (client) everything above, after a write

13.5 How Next.js extends fetch

One thing that trips people up: fetch on the server does not behave like fetch in the browser. Next.js replaces the global fetch with an extended version that adds two of the layers above directly to the call. Next.js Critical First, it deduplicates identical requests within a single render: two components that fetch the same URL with the same options during one pass share one request. Second, it wires the call into the Data Cache, a persistent, cross-request store you control through the cache and next options. 

data/stats.tsexport async function getPublicStats() {
  const res = await fetch(`${API_URL}/stats`, {
    // Cache the result and treat it as fresh for an hour.
    next: { revalidate: 3600, tags: ["stats"] },
  });
  return res.json();
}

// Personalized or always-fresh reads opt out explicitly.
export async function getLiveQueue() {
  const res = await fetch(`${API_URL}/queue`, { cache: "no-store" });
  return res.json();
}
Next reads the options off fetch itself: this response is cached across requests and tagged, so a mutation can invalidate exactly this data later.

This is why the audit's blanket export const dynamic = "force-dynamic" plus no-store everywhere (§17) is so costly: it tells this extended fetch to skip the Data Cache on every call, throwing away a layer the framework hands you for free. The habit to build is the inverse: cache by default with a declared revalidate and tags, and reach for no-store only where the data is genuinely per-request. When you call through the database or an SDK instead of fetch, you don't get this automatically, which is exactly why §13.2's cache() and "use cache" exist to fill the gap.

13.6 SWR, in more depth

On the client, the whole model rests on one idea: the key is the identity of the data. Two components that pass the same key read the same cache entry; a component that passes null as its key makes no request at all. Everything else (deduplication, revalidation, mutation) hangs off that key. 

hooks/useJobStatus.ts"use client";
import useSWR from "swr";

export function useJobStatus(jobId: string | null) {
  return useSWR(
    // A null key disables the request until we actually have an id.
    jobId ? `jobs/${jobId}` : null,
    fetcher,
    {
      // Poll while the job runs; the last value stays visible between polls.
      refreshInterval: 3000,
      // Collapse duplicate requests for this key inside a 2s window.
      dedupingInterval: 2000,
    },
  );
}

The revalidation triggers are the reason SWR feels alive without any manual wiring: by default it refetches on window focus and on network reconnect, plus on whatever refreshInterval you set. Crucially, it never blanks the existing content to do so. The stale value stays on screen while the new one loads, and swaps in when it arrives. That is the stale-while-revalidate contract, and it is the client-side echo of the loading doctrine in §10: revalidation is shown alongside content, never in place of it.

Writes go through mutate, which is the client mirror of revalidateTag: instead of calling a parent back to refetch, you tell the cache that a key is stale and every reader of that key updates itself. Passing new data to mutate paints it optimistically and revalidates in the background, which pairs naturally with §18's useOptimistic for action-driven writes.

13.7 When client fetching is the right tool

Server-first does not mean the client never fetches. It means client fetching is a deliberate choice for the cases that genuinely call for it, not the default for everything. React Very important Those cases have a clear signature: the data is not needed at first paint, and it is born from an interaction, a poll, or rapidly-changing client state.

  • Data that only exists after an interaction: search-as-you-type results, autocomplete suggestions, a filter applied in the browser. There is nothing to render on the server because the input hasn't happened yet.
  • Content inside a dialog, drawer, or sheet that isn't part of the main page and is opened on demand. It isn't in the first paint, so loading it when the panel opens is correct, not a smell.
  • Live or polling data: a job status, a notifications badge, anything that changes while the user watches it.

The dialog case is the one worth showing, because it is the clean inverse of the God component: the panel and its data are both loaded only when needed. 

components/programs/RowActions.tsx"use client";
import { useState } from "react";
import dynamic from "next/dynamic";

// The drawer and its data are both born from the interaction: loaded on open.
const DetailsDrawer = dynamic(() => import("./DetailsDrawer"));

export function RowActions({ id }: { id: string }) {
  const [open, setOpen] = useState(false);
  return (
    <>
      <Button onClick={() => setOpen(true)}>Details</Button>
      {/* DetailsDrawer calls useDetails(id), a shared SWR hook, once mounted. */}
      {open && <DetailsDrawer id={id} onClose={() => setOpen(false)} />}
    </>
  );
}

The test is the one from §8.5, applied to data: if the content is part of what the page is, the server should fetch it; if it is something the page does in response to the user, a client hook is the right home. The failure mode the audit found is the first kind masquerading as the second: a whole page's primary data loaded client-side as if it were interaction-born, when it was the page all along.

Rule Scope Importance
All server data access lives in a dedicated data layer, wrapped in cache(), marked server-only. Next.js Critical
Shared, non-personalized data is cached cross-request with "use cache" and tagged for invalidation. Next.js Very important
