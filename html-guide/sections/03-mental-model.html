Chapter 3

The Mental Model

This is the pivot chapter. If you take one thing from this guide, take this: the model you learned from years of traditional React is not the model this stack is built on, and the ecosystem is moving away from it, not toward it.

Chapter 1 traced the direction of travel: thirteen years of platform history converging on server-first. This chapter is the practical consequence: the model itself. What actually happens when an App Router page renders, and exactly where the old instincts betray you.

And carry in the warning from Chapter 1: these are deeply opinionated systems, and the opinions are the price of the guarantees. What follows is not a style this guide happens to prefer. It is the model the platform's machinery assumes, and every deviation from it costs you some of the machinery.

The shift, concretely

In an SPA, the browser receives a nearly empty shell and a JavaScript bundle; after the bundle mounts, each component pulls its own data into place, and the page assembles itself in front of the user. The question that model trains you to ask is "how do I get data into my components?" In the App Router, the page arrives already assembled: the server had the data and rendered with it before the browser saw a single byte. The only question left is "which parts of my UI can't be finished on the server, and why?", and every such part is a cost to be justified.

3.1 What actually happens when a page renders

In the App Router, every component is a server component by default. When a request comes in, the server executes your component tree (running your async components, awaiting your data) and streams the result to the browser as HTML, immediately, including real content for everything that was knowable and reserved fallbacks for everything that wasn't. Client components (only the subtrees you explicitly mark with "use client") are the only parts that ship JavaScript, hydrate, and become interactive.

Three consequences of this model are worth internalizing, because they invert traditional-React instincts:

  • Data access is a render-time concern, not a lifecycle concern. A server component doesn't "mount and then fetch"; it simply awaits what it needs while rendering. There is no timing to coordinate, no "is the data here yet?" state to manage. An entire category of client-side complexity (effects, request state machines, race conditions, stale closures) exists only on the other side of the client boundary. This is the deeper reason backend code has always felt simpler than frontend code: the server deals in one request → one response, while the client juggles user interactions, network variability, browsers, extensions, ad blockers, and time itself. SSR moves work from the hard side to the easy side.
  • The bundle is the exception, not the app. Server components ship zero JavaScript. Your app's JS payload is exactly the sum of its "use client" subtrees, which is why boundary placement (§5) is an architectural decision, not a style preference.
  • Navigation re-renders on the server too. Client-side navigations fetch the new route's server output (the RSC payload), not JSON-for-you-to-assemble. Layouts persist without re-rendering; only the changing segments re-render. The router, not your state management, owns the page's identity.

The app directory is your app, not "routes"

It's tempting to see app/ as the router's configuration area: thin page.tsx files that immediately hand off to the "real" components living in components/. That inversion is exactly backwards. The app directory is the application: its structure, its layouts, its containers, its core content. Everything related to the core parts of a page belongs there; the pieces that slot into that scaffold are what live outside it.

This is also the answer to a question worth asking yourself: why does Next.js use file-based routing at all? Because the filesystem makes the page's composition statically knowable. Layouts nest by directory. Loading and error boundaries are files, so the framework knows where they are before any code runs. Code splitting falls out per-segment for free. Prefetching a link means the router already knows exactly what the destination needs. Every one of those capabilities depends on the tree being declared in the filesystem rather than assembled at runtime in the browser. A five-line page.tsx that delegates everything to a giant client component doesn't just "move code around"; it hides the entire page from the framework.

3.2 Why the old mental model bites you later

The dangerous thing about SPA-style code in the App Router is that it works at first. The page renders. The data arrives. Nothing warns you. The costs arrive later, on real networks, at real scale, and by then they're structural:

And the failure modes compound, because each one blocks the escape route from the others:

Habit you keep Tool you lose
Fetch after hydration (effects, client query hooks) Streaming and loading.tsx: there's nothing to stream; the server finishes instantly with an empty shell.
"use client" at the page/layout level Server components below it: the entire subtree is client forever; every child you add ships to the bundle.
Requests the server never sees The whole caching model: "use cache", revalidation, request dedupe. You rebuild caching by hand, per hook.
Mutations via hand-rolled API routes Actions, revalidatePath/revalidateTag: read-your-writes consistency becomes your problem, solved with things like consistency tokens.
Client state for tabs, filters, visibility Shareable URLs, server-resolvable first render, and the router's back/forward behavior: all gone at once.

Read the left column against our own codebase and the pattern is uncomfortable; §18 does exactly that, file by file. The point of this chapter isn't blame; every one of those habits was the correct professional instinct in 2019. The point is that they are instincts, and instincts don't update from warnings; they update from understanding the machine underneath. That's what Parts A through C are for.
