Chapter 17 · Part D: Applied

Signs You're Doing It Wrong

A field guide to the tells. If you catch yourself doing one of these, you've probably drifted off the server-first path. Each sign says what it usually means, names its honest exception, and links to the chapter that fixes it.

These are smells, not sins. Every one of them has a legitimate exception, and every one of them has a real example in §18, because we are all of them today. The point of a checklist is speed: something feels off, you scan, you find the row, you follow the link. Read it that way. But before the list, the single reframe that makes most of it unnecessary.

17.1 One question underneath all of them

Almost every sign below is a symptom of asking the wrong question first. The instinct we carry from years of client React is: "how do I get this data to this component?" That question already assumes the component fetches, in the browser, after mount. It smuggles the whole broken model in through the phrasing. The right question, asked before any other, is blunter: "why can't this be on the server?" And when the answer is a real one (it genuinely needs the browser), the immediate follow-up is "how far down can I push it?" You are hunting for the smallest leaf that actually needs interactivity, not reaching for a directive at the top of the file.

17.2 The questions to keep asking

Make these reflexive. If you ask them honestly on every component, most of the signs below never get a chance to appear.

  • Why can't this be on the server? Not "can it," why not. Demand a concrete answer (it needs an event handler, browser state, an interaction). "It's easier this way" is not an answer.
  • If it truly can't, how far down can I push the boundary? What is the smallest piece that actually needs the browser? Everything else stays on the server.
  • Am I about to write a spinner or a loading flag? What is rendering it, and why isn't that the boundary's job instead of the component's?
  • Does the parent holding this data actually use it? Or is it just a pass-through wire I'll have to maintain forever?
  • Should this live in the URL? If it describes where the user is or what they're looking at, the request already carries it; the server can resolve it.
  • Is this import needed in the first paint? If not, where is the dynamic boundary that keeps it out of the initial bundle?

17.3 The boundary is in the wrong place

The sign What it means, and where it's fixed
"use client" sits on a page or layout. A directive at the top of a route segment forces everything beneath it into the browser, usually just to read params or run one handler. Push it to the leaf that needs it. Fixed in §5.2 and §5.3. Exception: a route that is genuinely interactive end to end, which is rare and worth a hard second look.
One file holds a pile of components. Especially in the app directory: it hides the boundary, blocks code splitting, and grows into a God component. One component per file, interactivity isolated. Fixed in §15.
One component owns fetching, UI state, and callbacks. That is the God component (or God hook): a single boundary that pulls the whole subtree client-side and couples everything to one object's shape. Fixed in §5.9 and §13.4.
"use client" is your first move, not your last resort. If adding the directive is the reflex rather than the justified exception, the model is inverted: the browser is a cost to be argued for, not the default. Fixed in §1 and §5.1.

17.4 Data is fetched the wrong way

The sign What it means, and where it's fixed
You're fetching inside a useEffect. First-render data belongs on the server; the effect + state + isLoading triple is the tell you're rebuilding by hand what the framework does for free. Fixed in §4 and §14.3. Exception: data that only exists after an interaction (search-as-you-type, autocomplete) does load client-side, but through a shared hook, never a raw effect.
A mutation goes through a Next.js API route. A server action replaces the hand-written POST endpoint and gives you end-to-end type safety and cache revalidation for free. Fixed in §5.7 and §19.
A first-render read goes through a proxy route. If the data isn't born from an interaction, the server should fetch it directly, one hop, before paint, not bounce it through a route handler after hydration. Fixed in §4; seen in the wild in §18. Exception: reads genuinely first needed after an interaction.
Queries are chained: one waits on another's result. Dependent, enabled-gated client queries serialize round-trips that a server component resolves in a single pass with Promise.all. Fixed in §12.2.

17.5 Components are wired together that shouldn't be

The sign What it means, and where it's fixed
A parent fetches data and hands it to several children. Let each child ask for its own data; deduplication makes the repetition free, and the parent stops being a distribution hub. Fixed in §13 and §14.
A child receives a prop the parent never uses. Passing anything through a parent that doesn't need it is a wire you will maintain forever for nothing. Components should take only what they themselves render. Fixed in §13.
A child calls back up so the parent can refetch. onSuccess then refetchAll() is orchestration. Invalidate the cache instead (revalidateTag, router.refresh, SWR mutate) and every reader updates itself, no wire required. Fixed in §5.8 and §13.4.

17.6 Loading states and containers are misplaced

The sign What it means, and where it's fixed
A component renders its own spinner. Components don't own loading states; the Suspense boundary above them does. A component that manages its own isLoading is doing the boundary's job badly. Fixed in §10.
The fallback includes the container the content sits in. The frame (card, table shell, page header) is known at first render and belongs outside the boundary, rendered on the server; only the unknown contents suspend. Putting the container in the fallback means it gets thrown away and rebuilt. Fixed in §9 and §10.
The suspending component brings its own container. Same root cause, mirror image: the frame lives inside the child that suspends instead of in the layout, so it flickers in with the data instead of being there from the first byte. Fixed in §9.
Containers aren't sized on the server. If the box isn't rendered immediately and reserving accurate space for both the fallback and the real content, the page shifts when data lands. Reserve the space up front. Fixed in §9.
A skeleton is standing in for content that was knowable. Skeletons exist to hold space for the unknown. A skeleton over the whole page, or over inputs, selects, buttons, toolbars, headings, and other structure that required no data, means the boundary swallowed content that could have painted finished on the first byte; the user is watching placeholders for things nobody had to wait for. Wholesale page skeletons need an exceptional reason to exist. Draw the boundary around the data, not around the region it happens to sit in. Fixed in §10 and §4.

17.7 State is living where the URL should own it

The sign What it means, and where it's fixed
Tabs are held in useState. A tab is where the user is. That belongs in the route (a segment or a search param), not in client state that resets on reload and can't be linked to. Fixed in §8.3.
The browser reads a query param to decide what to show. Reading ?x= in a client component and conditionally rendering on it turns the URL into a client-state store the server can't use, and delays the content behind hydration. If output depends on the query string, resolve it on the server from the request. Fixed in §8.2. Exception: genuinely ephemeral, client-only UI (an open menu, a hover state) that has no business in the URL at all, covered in §8.5.

17.8 Too much JavaScript ships on first render

The sign What it means, and where it's fixed
A heavy client package loads on first paint. Charting libraries, rich-text editors, and date pickers pulled into the initial bundle inflate time-to-interactive for UI most users never touch on load. Fixed in §6.
Something not needed at first paint has no dynamic boundary. If it isn't on screen immediately (dialogs, drawers, below-the-fold panels), it should load on demand with next/dynamic, not sit in the bundle every visitor downloads. Fixed in §6.3. Exception: small modules that are needed right away, where a dynamic import only buys you an extra round-trip.
How to use this list

Don't treat it as a purity test. Treat it as a set of tripwires: when you catch yourself doing one, stop and ask the question from §17.1 before you write the next line. Sometimes the honest answer lands you on the exception, and that's fine, the exceptions are real and named on purpose. But most of the time the tripwire is telling you the truth, and the fix is one link away. The goal isn't zero client components; it's that every one of them is a decision you could defend out loud.
