Chapter 5 · Part A: Maximize the Known

Client/Server Boundaries

The question is never "does this component need "use client"?" It's "how far down can I push the boundary?" This chapter is about what the directive actually does, what genuinely requires the client, and the patterns for isolating interactivity into the smallest possible leaves.

5.1 What "use client" actually means

"use client" is not a per-component setting, and it isn't "this component is interactive." It is a module-graph marker: it declares the point where the server hands the tree to the browser. The directive goes at the top of a file, and from that file onward, every module it imports, and everything those import, becomes client code: bundled, shipped, parsed, and hydrated. React Critical

That's why one careless directive is never one component's problem. A "use client" at the top of a page doesn't make a page interactive: it drags the page's entire import graph across the boundary. Components that render pure markup, utilities that format dates, the icon set, the table internals: all of it ships and hydrates, whether or not it ever does anything a server component couldn't have done for free.

Three mechanical facts complete the picture: React Critical

  • Client components still render on the server once. "Client" doesn't mean "skips SSR": their initial HTML is server-rendered, then hydrated in the browser. What you lose at the boundary isn't the first paint; it's async/await data access, zero-bundle rendering, and everything else in Part A.
  • Props crossing the boundary must be serializable. The server sends them over the wire: plain objects, arrays, strings, numbers: yes; functions, class instances, DB handles: no. (Server Actions and JSX are the special, allowed exceptions.) If you're fighting serialization errors, the boundary is probably in the wrong place.
  • The dependency arrow points one way. A client module can't import a server component; importing it would just drag it across and make it client code. Server content gets into client subtrees only by being passed through, already rendered (§5.4).

5.2 What genuinely requires the client, and what doesn't

The honest list of things that cannot run on the server is short:

Needs the client Does not need the client
State that changes from user input: useState, useReducer Fetching and awaiting data: that's what server components are for
Event handlers: onClick, onChange, onSubmit Rendering data: lists, tables, conditionals, formatting, markup of any complexity
Effects and lifecycle: useEffect (and it had better not be fetching; §10) Reading route input: params and searchParams arrive as page props (§8)
Browser APIs: localStorage, observers, media queries, window Composition: laying out children, choosing variants, mapping data to components
Interactivity hooks: useRouter, useOptimistic, useTransition Authorization decisions: cookie/session reads belong on the server, with redirect()
Third-party components built on any of the above Anything whose output is the same HTML for the same inputs

Read the right column again: it's most of every page. That's the empirical reason "use client everywhere" is backwards: the default assumption should be that a component is server-renderable, with the burden of proof on the exception. When a component needs one item from the left column, the answer is not to convert the component; it's to evict that one item into a leaf and keep everything else on the server.

5.3 Pushing the boundary down

Next.js Critical The method, applied every time something needs interactivity:

  1. Name the interaction atoms. What does the user actually do here? Type in a search box. Click an export button. Open a row menu. Those atoms, not the sections containing them, are your client components.
  2. Extract each atom into its own leaf file. A SearchInput, an ExportButton, a RowActionsMenu: each with "use client" at the top, each owning exactly its interaction and nothing else.
  3. Keep the structure server-side. The section, the card, the toolbar row, the table markup: all of it stays server; it renders data, it doesn't handle input.
  4. Where interactivity must wrap content, pass the content through. A collapsible panel, a dialog, a hover card: the shell is client, but its children arrive server-rendered (§5.4).

This is also why no "use client" in the app directory is our house recommendation. Next.js Very important The app directory is the scaffold: pages, layouts, structure, core content (§3). If a file in app/ carries the directive, the scaffold itself has crossed the boundary, and everything slotted into it goes along. Client code lives in leaf components, imported into the scaffold. Legitimate exceptions exist (error.tsx is required to be a client component; a page that is genuinely one interactive surface, like a canvas editor), but each one should be an explicit decision, not a reflex to make a hook error go away.

5.4 Getting server content inside client shells

The pattern that makes leaf boundaries workable: a client component can't import server components, but it can receive them. children (and any JSX-valued prop) is rendered on the server first; the client shell receives the finished output and slots it in. The interactive wrapper ships to the browser; its contents don't. React Critical

✕ Wrapper converts its contents
CollapsibleSection.tsx"use client";

/* Importing it drags it across the boundary:
   ActivityFeed is client code now, fetch and all. */
import { ActivityFeed } from "./ActivityFeed";

export function CollapsibleSection() {
  const [open, setOpen] = useState(true);
  return (
    <section>
      <button onClick={() => setOpen(!open)} />
      {open && <ActivityFeed />}
    </section>
  );
}
✓ Wrapper receives server-rendered children
CollapsibleSection.tsx: client shell, knows nothing"use client";
export function CollapsibleSection({ children }) {
  const [open, setOpen] = useState(true);
  return (
    <section>
      <button onClick={() => setOpen(!open)} />
      {open && children}
    </section>
  );
}
page.tsx: server composes through the shell<CollapsibleSection>
  {/* ActivityFeed stays a server component; it
      fetches, renders, and ships 0 KB of JS; it

  <ActivityFeed programId={id} />

This slot pattern is the workhorse for every interactive shell: dialogs, sheets, tabs, accordions, tooltips, hover cards. The shell owns open/closed and nothing else; what's inside keeps all its server privileges. It's also the answer to context providers: a ThemeProvider or QueryClientProvider is a client component, but rendered as a thin wrapper around {children} near the root, it converts nothing below it: the children pass through, still server components.

5.5 Third-party components and boundary hygiene

The rest of the category, the housekeeping that keeps boundaries where you put them:

  • Wrap third-party interactive components in your own "use client" file. Next.js Critical External UI libraries use state and events throughout, but many don't declare "use client" (it's a bundler convention, not a JS standard; older packages predate it). Importing them from a server component fails or silently misbehaves. One-line wrapper file: "use client"; export { Carousel } from "acme-carousel";. Now it has a declared boundary, and your import graph documents exactly where the client zone starts. Bonus: the wrapper is your seam for swapping the library later (§14). Worked through with examples in the subsection below.
  • Poison-pill your server-only modules. React Very important import "server-only" at the top of the data layer (§13) turns "someone imported data/programs.ts from a client component" into a build error instead of a leaked API key. client-only exists for the reverse.
  • Mind the environment variables. Only NEXT_PUBLIC_* vars exist in client bundles, and all of them are shipped to every visitor. If a boundary move suddenly requires making a variable public, that's the boundary telling you it's in the wrong place. Next.js Critical
  • Don't reach for client hooks to read route input. params and searchParams arrive as server page props; useParams/useSearchParams in a client page is usually the reason the page went client in the first place (§8). Same for cookies and headers: next/headers, on the server.
  • Authorization is a server decision. A guard component that fetches "am I allowed?" after hydration paints the page first and asks permission later. The cookie is on the server; check it in the layout or page and redirect()/notFound() before anything renders. Next.js Critical

Design-system components: ship the structure and the leaves separately

Everything this chapter says about applications applies with extra force to our monorepo UI library, because a library component's boundary decision is made once and inherited by every consumer. The rule: a library component with interactive parts exposes its non-interactive structure and its interactive leaves as separate components, so the consuming application gets to place the boundary, not the library. React Critical

The canonical mistake is the all-or-nothing component configured through data. A sidebar that takes items={[{ icon, label, onClick }]} is one fused component: it must carry "use client" (it wires handlers), and because functions cannot cross the server-client boundary as props, the page that renders it is forced client too, just to be able to define those onClicks. One prop signature has converted two trees.

The one part that genuinely needs an event handler, isolated in its own file so that importing the container never drags it across the boundary.

Button-style items get consumed by small app-level client leaves, like the SignOutItem above, that render SidebarButtonItem and own the handler themselves, exactly the self-contained-leaf pattern of §5.7. The library provides the pieces; the application decides where the client zone starts.

5.6 Client components that read the URL get their own Suspense boundary

One boundary case is mechanical enough to deserve its own pattern: it sits exactly at the intersection of this chapter and §8 (the URL as state). A client component that calls useSearchParams() must render inside a <Suspense> boundary. Next.js Critical

Why: search params are per-request data. While Next.js prerenders the static shell of a page, there is no request, so the value genuinely does not exist yet, and a client component that insists on reading it from the browser has to be able to suspend until it does. What the boundary buys, concretely:

  • The shell stays static. The rest of the page prerenders and streams normally; only the reader of the search params waits for request time.
  • The bailout is scoped. Without a local boundary, the client-side-rendering bailout climbs to the nearest ancestor boundary, often deopting the entire page to client rendering to accommodate one filter input. With one, the "dynamic hole" is exactly the size of the leaf.
  • The build passes under PPR. With cacheComponents, a request-time read outside a Suspense boundary isn't a deopt; it's an error. The boundary is how you declare "this part is dynamic, on purpose."

Because forgetting the wrapper is easy and the failure is confusing, make the boundary part of the component itself; consumers should never need to remember it: 

SearchInput.tsx: the boundary is part of the component's public shape"use client";

export function SearchInput(props: SearchInputProps) {
  return (
    <Suspense fallback={<SearchInputSkeleton />}>
      <SearchInputInner {...props} />
    </Suspense>
  );
}

// Only the inner component reads the URL, so only it ever suspends.
function SearchInputInner(props: SearchInputProps) {
  const params = useSearchParams();
  // …
}
The exported component bakes its own Suspense boundary in, so no call site can forget it. The fallback mirrors the input's geometry (same reserved space, §9), so nothing shifts when it resolves.

Two clarifications to keep the pattern honest. First, this applies to the client read: a server page reading searchParams from its props doesn't need this; the page is simply dynamic at that point, which is §8's territory. Reach for the client read only in leaves that write the URL and need the live value interactively (filter inputs, sort toggles). Second, useParams and usePathname don't require this: route params and pathname are knowable from the route structure; it's specifically the query string that is per-request. See it in action in §10.5's worked example, where the boundary also carries an explanatory comment.

5.7 Encapsulation in practice: the self-contained button

Everything this chapter has argued comes to a point in one concrete pattern. The purest expression of "push the boundary down" is an interactive leaf that owns its entire interaction: the click, the pending state, the call to the server, and any UI the interaction spawns. React Critical Nothing above it participates, which is precisely what lets everything above it stay a server component.

✕ The page owns the interaction
app/programs/[id]/page.tsx"use client";

/* One button's mechanics hoisted the whole
   page into the client. */
export default function ProgramPage() {
  const [isPublishing, setPublishing] =
    useState(false);

  return (
    <ProgramHeader>
      <Button
        loading={isPublishing}
        onClick={async () => {
          setPublishing(true);
          await api.publish(programId);
          setPublishing(false);
          refetchProgram();
        }}
      >
        Publish
      </Button>
    </ProgramHeader>
  );
}
✓ The leaf owns the interaction
app/programs/[id]/page.tsx/* Server component: no "use client",
   no handlers, no loading flags. */
export default async function ProgramPage(
  { params }
) {
  const { id } = await params;
  const program = await getProgram(id);

  return (
    <ProgramHeader program={program}>
      <PublishButton programId={id} />
    </ProgramHeader>
  );
}

The button itself is small, boring, and completely portable. It calls a server action, and useTransition gives it a pending flag for the duration: its loading state, owned locally, exactly as the loading doctrine demands (§10.3; a pending interaction indicator on the control is the legitimate kind of local loading state; it reserves no content space and replaces nothing): 

components/program/PublishButton.tsx"use client";

import { useTransition } from "react";

/* Yes, a client component can import a server action. The "use server"
   module doesn't pull server code into the bundle: the client receives a
   typed reference, and calling it becomes a network request the framework
   manages. This is the one import that crosses the boundary by design. */
import { publishProgram } from "@/actions/programs";

/* The entire interaction lives here: the click, the pending state, and the
   call to the server. Nothing above this component knows any of it exists. */
export function PublishButton({ programId }: { programId: string }) {
  const [isPending, startTransition] = useTransition();

  return (
    <Button
      loading={isPending}
      onClick={() =>
        startTransition(async () => {
          /* Actions return results rather than throwing across the network:
             respond to the failure right where the interaction lives. */
          const { error } = await publishProgram(programId);
          if (error) toast.error(error);
        })
      }
    >
      Publish
    </Button>
  );
}

Pause on that import, because it's the part people don't believe: a client component imported a server function and called it in a click handler. That is exactly what server actions are for. The "use server" directive turns the module's exports into references the client can hold; importing one adds no server code to the bundle, and invoking it makes a typed, framework-managed request to the server (the imports that are forbidden across the boundary are server components and server-only modules, per §5.1). So the boundary can sit at the button and the mutation still runs where it belongs: no API route, no fetch wrapper, no client-side secret handling.

The same rule covers everything an interaction spawns. A dialog opened by a button lives inside the button component that opens it, as do popovers, dropdown menus, drawers, and every other floating element. React Critical The open/closed state is interaction state; it belongs to the leaf. The moment the dialog's state lives in the page, the page is client, and every sibling of that dialog pays for one confirmation prompt.

Encapsulating the dialog also hands you a bundle win for free: since the dialog is invisible until its button is clicked, its JavaScript has no business in the first-render bundle. Load it with next/dynamic and render it conditionally: the chunk downloads on first open, and until then the page carries only the button (§6's subject, met here in its most common form): 

components/program/DeleteProgramButton.tsx"use client";

import dynamic from "next/dynamic";

/* The dialog's JavaScript isn't needed until the button is clicked, so it
   doesn't belong in the first-render bundle (§6). next/dynamic splits it
   into its own chunk, fetched on demand. */
const ConfirmDialog = dynamic(() =>
  import("@/components/dialogs/ConfirmDialog").then((m) => m.ConfirmDialog)
);

/* The dialog is an implementation detail of the button that opens it. It
   mounts here; the page never knows a dialog exists. */
export function DeleteProgramButton({ programId }: { programId: string }) {
  const [open, setOpen] = useState(false);

  return (
    <>
      <Button variant="danger" onClick={() => setOpen(true)}>Delete</Button>

      {/* Mounted only once opened, so the chunk loads on first click. */}
      {open && (
        <ConfirmDialog
          open
          onOpenChange={setOpen}
          title="Delete this program?"
          onConfirm={() => deleteProgram(programId)}
        />
      )}
    </>
  );
}

Look at the wire count. The parent hands each of these components an id: identity, the one prop that's always legitimate (§12). That is the entire contract. No onPublish, no isPublishing, no dialogOpen, no refetch callback. Which raises the obvious question: when the action finishes and the page's data is stale, who tells the parent?

5.8 Refreshing the parent without wiring it to the child

Two honest answers exist, and the difference between them is most of this guide's thesis in miniature.

Approach 1: a refetch context. Wrap the region in a provider that owns the query and exposes its re-execute function; the button calls useRefetch() and stays ignorant of who actually refires: 

The context approach: workable, but note what it costs"use client";

const { refetch } = useRefetch();

return (
  <Button
    loading={isPending}
    onClick={() =>
      startTransition(async () => {
        await publishProgram(programId);
        refetch();
      })
    }
  >
    Publish
  </Button>
);
Inside the button: no prop threading, and no knowledge of who the parent is.

This is genuinely better than drilling an onSuccess callback through three layers: the intermediate components stay clean. But look at what it presumes: someone above is fetching in client land, or there would be no refetch to offer. The provider and the query pull the boundary back up the tree, and we're client-rendering a region to solve a problem the platform already solves. Acceptable inside a genuinely client island (see the SWR variant below); the wrong default for a page.

Approach 2: the server is the source of truth. Next.js Critical The mutation already runs on the server; let the server decide what's stale. The action invalidates the data it changed, Next.js re-renders the server components that read that data, and a fresh RSC payload (§4.5) streams back and merges in place. Nobody calls anybody: 

actions/programs.ts"use server";

import { revalidateTag } from "next/cache";

export async function publishProgram(id: string) {
  try {
    await db.program.update({ where: { id }, data: { status: "published" } });
  } catch (e) {
    /* Returned, not thrown: the client handler decides how to surface it
       (the toast in §5.7). */
    return { error: "Could not publish the program. Please try again." };
  }

  /* The server is the source of truth. Invalidating the tag re-renders every
     server component whose data carried it; the parent page updates without
     ever being told to. revalidatePath() is the coarser equivalent, and
     router.refresh() covers mutations that didn't go through an action. */
  revalidateTag(`program-${id}`);
  return {};
}

Reads follow the exact same principle: the URL plays the role the cache tag played. A search input doesn't call an onSearch prop; it writes its query param and lets the route re-render: 

components/table/SearchInput.tsx (inner; see §5.6 for the baked-in boundary)"use client";

function SearchInputInner() {
  const router = useRouter();
  const searchParams = useSearchParams();

  return (
    <SearchField
      onChange={(value: string) => {
        const params = new URLSearchParams(searchParams);
        if (value) params.set("q", value);
        else params.delete("q");

        /* A client-side transition to the same route: the server page
           re-renders with the new searchParams and streams fresh rows into
           the table. The input doesn't know a table exists; the table
           doesn't know the input exists. The URL is the only wire. */
        router.replace(`?${params.toString()}`);
      }}
    />
  );
}

This is the pattern §10.5's worked example builds out in full (with the transition-based stale indicator), and §8 makes the general case for the URL as state. Notice what the two halves share: the leaf writes to shared infrastructure (the cache, the URL) and the parent re-renders because its inputs changed, never because a child called it. That is also §12's core rule, seen from the boundary side.

When the parent is legitimately client: the key is the contract

Sometimes the parent has earned its "use client", and the canonical case is UI that doesn't exist until the user does something. A drawer that slides open off a row click, a details popover, a preview panel: none of these are on the page when the server renders it, so their content can never ride the first response. When they mount, after the interaction, they fetch client-side, and useSWR is the right tool. The encapsulation pattern survives intact; only the shared infrastructure changes. SWR's cache is keyed, and the key replaces the callback: React Very important 

components/program/ProgramDrawer.tsx"use client";

import useSWR from "swr";

export function ProgramDrawer({ programId, onClose }: ProgramDrawerProps) {
  const { data: program, isLoading } = useSWR(
    ["program", programId],
    () => fetchProgram(programId)
  );

  return (
    <Drawer onClose={onClose}>
      {/* Loading ⊥ data ⊥ empty, handled per §10.6; elided here. */}
      <ProgramDetails program={program} isLoading={isLoading} />
      <PublishButton programId={programId} />
    </Drawer>
  );
}
This component is legitimately client: it opens after an interaction, so the server's first render never contains it, and its data is necessarily fetched after mount. It fetches by key, and passes the button an id (identity, nothing else), exactly as the server version did. 
components/program/PublishButton.tsx (SWR flavor)"use client";

import { mutate } from "swr";

export function PublishButton({ programId }: { programId: string }) {
  const [isPending, startTransition] = useTransition();

  return (
    <Button
      loading={isPending}
      onClick={() =>
        startTransition(async () => {
          await publishProgram(programId);
          await mutate(["program", programId]);
        })
      }
    >
      Publish
    </Button>
  );
}
The button revalidates the key when its mutation lands. Every subscriber of that key refires on its own; the button holds no reference to the parent, receives no refetch callback, and works under any parent that uses the same key.

Server tag, URL param, SWR key: three spellings of one idea. The leaf and the parent agree on a name for the data, and communicate by invalidating the name. The refetch mechanics live in the infrastructure (§13), not in a callback prop, so the boundary stays at the leaf no matter which spelling the page uses.

5.9 The God component: one boundary to lose everything

Now invert every rule in this chapter at once, because our codebase does. Put a "use client" component (or its more respectable-looking cousins, a provider or a useXManager() hook) at the top of a tree, and have it do three jobs: fetch the data, own the UI state, and dispense the callbacks, flowing all of it down through props and context: 

The shape to fear: three jobs in one hook"use client";

export function useProgramsManager() {
  const [programs, setPrograms] = useState<Program[]>();
  const [isLoading, setIsLoading] = useState(true);
  const [filters, setFilters] = useState<Filters>(DEFAULT_FILTERS);
  const [selectedId, setSelectedId] = useState<string | null>(null);
  const [isSaving, setIsSaving] = useState(false);

  useEffect(() => {
    /* Fetch #1 of the tree: nothing below renders content until this lands. */
    fetchPrograms(filters).then((data) => {
      setPrograms(data);
      setIsLoading(false);
    });
  }, [filters]);

  async function saveProgram(input: ProgramInput) { /* … */ }
  async function deleteProgram(id: string) { /* … */ }

  return {
    programs, isLoading,
    filters, setFilters,
    selectedId, setSelectedId,
    isSaving, saveProgram, deleteProgram,
  };
}
Three jobs in one hook: it fetches, it owns everyone's UI state, and it defines everyone's callbacks. Every consumer below becomes a client component wired to this one object's shape.

That's the hook spelling. The same disease wears a component costume just as often: a page or container that fetches everything in sight, holds state it never reads, and threads all of it down through layers that are nothing but couriers: 

app/programs/page.tsx: the component spelling"use client";

export default function ProgramsPage() {
  /* Fetches #1, #2, and #3, none of which the page itself renders. It is
     collecting cargo on behalf of components two and three levels down. */
  const { data: programs, isLoading } = useSWR("/api/programs", fetcher);
  const { data: me } = useSWR("/api/me", fetcher);
  const { data: orgs } = useSWR("/api/organizations", fetcher);

  /* State the page holds only so it can hand it to descendants. The page
     never filters anything and never selects anything. */
  const [filters, setFilters] = useState<Filters>(DEFAULT_FILTERS);
  const [selectedId, setSelectedId] = useState<string | null>(null);

  /* Every layer below is a courier. SectionLayout doesn't use `user` or
     `orgs`; the toolbar doesn't select; the table hands `selectedId` on
     down to Row, which hands it to Cell. Boxes carrying boxes. */
  return (
    <SectionLayout user={me} orgs={orgs}>
      <ProgramsToolbar
        user={me}
        filters={filters}
        onFiltersChange={setFilters}
      />
      <ProgramsTable
        rows={programs}
        isLoading={isLoading}
        filters={filters}
        selectedId={selectedId}
        onSelect={setSelectedId}
        onDelete={(id) => deleteProgram(id)}
      />
    </SectionLayout>
  );
}

Read the page's own render: it uses none of what it gathered. Every fetch, every piece of state, every callback exists on behalf of someone else: the page is a warehouse, and SectionLayout, ProgramsToolbar, and ProgramsTable are its delivery routes (the coupling-layer autopsy of §12.1, wearing its boundary costume). And the threading doesn't stop where the snippet does: selectedId rides through ProgramsTable into Row into Cell, coupling four signatures to one piece of state that exactly one of them reads.

Call this what it is: a God component. It is hazardous in a way ordinary bad code isn't, because the damage isn't local. The "use client" sits at the top, so the module graph (§5.1) drags the entire subtree across the boundary: every section, table, row, and cell below it is client-rendered now, whether it has an event handler or not. And that means the App Router's server-first machinery isn't just unused down there. It is literally unavailable:

  • No server components below it. An async component can't render under a client parent (only pass through one, via slots, §5.4, which this shape never uses because it imports everything it renders).
  • No first-paint content, no cached pages. The data loads after hydration, so the first response is a shell: nothing to stream (§10.2), nothing for the route cache to keep (§4.4). Every visitor re-pays every fetch, forever.
  • The timing problems return. Content depends on request ordering again: waterfalls (§11.4), nested spinners (§4.2), layout shift as each answer lands (§9).
  • Maximum wiring. Every consumer is coupled to the manager's return shape; every new feature threads more props and callbacks through components that don't use them. This half of the autopsy, the coupling half, is §12.4's subject.
  • Refactor gravity. Children written against the manager's context can't be lifted out or rendered on the server without rewriting them, so the cheapest place to add feature N+1 is inside the God component, which is how it got this big last time.

The fix is not to split the God component into three smaller gods. It's to invert the direction of everything it does: data flows down as rendered HTML instead of props (§5.3), interactions live in self-contained leaves instead of dispensed callbacks (§5.7), and staleness flows through the cache and the URL instead of refetch functions (§5.8). Each child stops being a puppet of the manager and becomes a component again.

5.10 Server actions and the HTTP middleman

§5.7's button called a server action and moved on. It is worth stopping on what that server action actually is, because it is the single biggest lever for pulling mutations back across the boundary, and the reason the 73 pass-through proxy handlers the audit found (§17) are unnecessary.

A server action is a typed remote procedure call. When you mark an async function "use server", the bundler splits it out of the client graph, leaves a reference in its place, and the framework generates an endpoint for it. Calling it from the client serializes the arguments, sends them to that endpoint, runs the function on the server, and serializes the result back. You write an ordinary function call; the framework does the transport. Because the function's signature is the contract, the types flow from the component to the server and back with no schema to hand-maintain and no client to keep in sync. The API surface (the directive, useActionState, useFormStatus, <Form>) is catalogued in §18.2; what matters here is the architecture. Next.js Critical

The reason it matters beyond ergonomics is what you lose when you put an HTTP layer you own between the UI and the data.

When a server action reaches your data directly, through Prisma or a service SDK, a failure is a typed value you handle precisely: the record does not exist, the user is not allowed, a constraint failed, each one distinct and catchable at the call site. Route that same mutation through a Next.js API route that proxies to another HTTP service (the Tracker pattern from §17) and every one of those distinct failures is flattened into a status code on the way out and reconstituted on the way back. You also inherit a second set of failure modes that have nothing to do with your domain: network errors, timeouts, retries, serialization mismatches. Each middleman is one more place the types are lost and one more surface of errors the caller has to account for.

Fewer middlemen

The principle is blunt. Use server actions that talk to your real backend services directly, rather than proxying mutations through Next.js API routes on the same app. Every HTTP hop you remove is type safety you keep, latency you save, and a class of errors you no longer have to handle. And once the mutation lands, the parent refreshes through the cache, not a callback (§5.8, §13.2), so the write stays as decoupled as the read.
