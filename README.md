# The App Router Guide (repo)

This repo builds **The App Router Guide**, a 20-chapter document teaching server-first Next.js 16 /
React 19 patterns. This README is for maintaining the repo and producing the distributables. If you
are here to _read_ the guide, build it (below) and open
`build/output/app-router-guide_html/index.html`; the recipient-facing explanation of the outputs
lives in `build/README.md`.

## Layout

- `src/` is the source of truth: Astro pages (`src/pages/sections/NN-slug.astro`), components,
  layouts, `src/data/toc.js`, and styles. All authoring happens here. Never hand-edit anything under
  `build/output/`; the build clears and regenerates it.
- `public/assets/` holds runtime assets copied into the build: `nav.js` (sidebar, search, pager,
  code-wrap, and the dev-only annotation layer), plus two **generated** files (`style.css`,
  `search-index.js`) that are gitignored and rebuilt by the scripts below.
- `build/` contains a committed `README.md` for recipients and a gitignored `output/` with every
  distributable. Zipping `build/` is the intended way to send the guide out.
- `supplementary/` holds the working documents: `working-notes.md` (the running content queue; note
  its DO NOT AUTOMATICALLY ADDRESS sections), `audit.md`, and `references.md` (the external-sources
  ledger that §20 renders).
- `PROJECT.md` is the project tracker and the canonical list of authoring conventions (naming,
  formatting rules, diagram style, snippet rules). Read it before writing content.

## Setup and daily workflow

```
npm install        # once; brings in astro, prettier, and dart-sass
npm run dev        # compiles SCSS, then starts the Astro dev server
```

Edit under `src/`, view on the dev server. Styles are SCSS: `src/styles/style.scss` plus
`src/styles/partials/_*.scss`. `public/assets/style.css` is generated by `npm run css` (which `dev`
and `build` run first); never edit the generated file. `npm run css:watch` gives live recompiles
while styling.

## Building the outputs

```
npm run build      # the multi-page HTML site -> build/output/app-router-guide_html/
npm run dist       # everything: html + markdown, folder + single-file forms
npm run dist -- --output=md --packaging=file    # or any subset
```

`npm run build` chains: SCSS compile, `astro build`, `scripts/postbuild_relativize.py` (relativizes
asset URLs so `file://` works, deletes the notes ledger from the output, and strips the dev-only
blocks from `nav.js` and `style.css`; it fails the build if the strip markers are missing), prettier
over the output, and `scripts/build_search_index.py` (writes `search-index.js` into both the build
and `public/assets/` so dev-server search works).

`npm run dist` (`scripts/build_dist.py`) additionally produces the single-file HTML
(`scripts/build_artifact.py --final`) and both markdown forms (`scripts/build_md.py`, a
deterministic HTML-to-markdown converter). All dist outputs are final: no draft tooling, prettier
formatted.

## The annotation / draft layer (dev only)

`nav.js` contains an annotation module: a DRAFT badge and a note mode for pinning review comments to
blocks on the page (including TOC rows and sidebar links, which are selectable without navigating).
Notes append to `public/page-notes.json`, the ledger that drives review rounds: open notes get
addressed, then marked `resolved` with a `resolution` explaining what changed.

This whole layer is development-only. It is gated to localhost at runtime and physically removed
from builds: the module sits between `/* @dev-only:start */` and `/* @dev-only:end */` markers in
`nav.js` (and its styles in `_draft-tools.scss`), and the postbuild step strips those regions and
excludes `page-notes.json`. Built output must never show a DRAFT badge or any annotation UI.

## Diagrams

Diagrams are hand-authored SVG inside `<Diagram>` components; the SVG is the source of truth. Every
diagram also carries a Mermaid twin in a `<pre slot='mermaid'>` (invisible in HTML; extracted into
`mermaid` code fences by the markdown build). The sync rule is strict: whenever a diagram's SVG
changes, update its Mermaid twin in the same edit, and never edit a twin independently. Mermaid
twins follow portability conventions (no init directives, in-diagram classDefs only, short one-line
cluster titles, `%%split%%` instead of invisible edges); the full ruleset is in `PROJECT.md`.

## Verification

After any content change: `npm run build`, then `python3 scripts/svg_lint.py` (diagram geometry) and
the ad-hoc gate we run before committing: link/anchor resolution across pages, HTML tag balance,
zero em dashes (U+2014), code-line width budgets (54/62 columns in compare columns, 110/118
full-width), and markdown output checks (balanced fences, resolvable links, no missing Mermaid
twins, which `build_md.py` warns about on stderr).

## Conventions worth knowing before editing

The complete list is in `PROJECT.md`; the ones that bite fastest:

- Every code snippet lives in a `<Snippet>`; whole-snippet commentary goes in `<CodeCaption>`, not
  code comments. Verdict-bearing snippets carry `v-good`, `v-bad`, or `v-warn` on the `pre`.
- One exported component per example file; no blank line after `"use client"` / `"use server"`.
- Inserting or removing a chapter means renumbering everything: files, kickers, heading numbers,
  both TOCs (`src/data/toc.js`, `public/assets/nav.js`, `src/pages/index.astro`), and every `§`
  reference and href guide-wide, then running the full gate.
- Astro text treats braces as expressions: literal `{` `}` in prose must be `&#123;` / `&#125;`, and
  code blocks keep the `is:raw` attribute.
